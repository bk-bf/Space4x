# AGENTS.md: Space4x

How to work on this code as it is now. Plans, decisions and findings go in issues, pull requests and commit messages, not here.

## The code is the ground truth

If something is unclear, find out from the code: grep for it, read it, run it. Do not infer it from a document, a name, or from what a game like this usually does. State what you checked.

## Stack

SvelteKit 3 with Svelte 5 runes and strict TypeScript, built by `@sveltejs/adapter-static` as a single-page app (`ssr = false`, fallback `index.html`) so a desktop shell can wrap it later. pnpm only; never npm, npx or yarn (`pnpm dlx` for one-offs). Commit `pnpm-lock.yaml`.

Imports inside `src/` go through the `#lib/*` subpath import in `package.json` and name the file with its extension: `import { game } from '#lib/game/index.ts'`. SvelteKit 3 has no `$lib`.

Use runes (`$state`, `$derived`, `$effect`, `$props`); not the legacy `$:` syntax or stores.

## Game and gallery

Nothing mock is shown in the game build. `VITE_SPACE4X_GALLERY=1` selects the gallery build, which shows everything; `gallery` from `#lib/shell/mode.ts` is the only reader of it. In the game, `mockWorld()` has no sites (so no site scene, marker or fly-to button), `SCREENS` lists only screens with `mock: false` (so the top bar, F keys, `?screen=` and `isScreenId` ignore the rest).

Every entry in `screens/list.ts` carries `mock: boolean`. To make a screen real, change its `mock` to `false`; nothing else. New mock content (a scene, a list, a button) is wrapped in `gallery` so the game build never renders it. The gallery is built by `deploy/build` into `~/mockups/space4x-gallery/` (served by the mockups server at `/space4x-gallery/`), not by a separate script.

Tests: Playwright has two projects, each with its own dev server. `gallery` runs everything but `tests/game.spec.ts`; `game` runs `tests/layout.spec.ts` (states marked `mock` in `tests/states.ts` are skipped) and `tests/game.spec.ts`. A layout state that needs a mock screen or site goes in `tests/states.ts` as before; a site-only query also goes in `SITE_QUERIES`. Vitest runs with the gallery on (`vitest.config.ts`); `src/lib/shell/mode.test.ts` covers the game mode.

## Game state

`game` (from `#lib/game/index.ts`) is the one `Game`. Its fields are runes, so components read them directly and update when they change.

- `game.time` (ms, UTC), `game.elapsed` (game seconds since the start), `game.running`, `game.step` (seconds)
- `game.world`: `bodies`, `fleets`, `contacts` (each names its `system`), `systems` (stars, belt, jump points), `system` (the one the map shows); `game.events`; `game.status` (the top bar chips, read-only: see below)
- a body with `colony: true` is a colony, and the economy holds one site for it whose `worldBody` is that body's id (`siteById(bodyId)` finds it), so add a colony as a colonised body and an economy site together. A body with `parent` is a moon and `bodyPosition(body, bodies)` places it around that body
- `game.body(id)`, `game.fleet(id)`, `game.contact(id)`, `game.starSystem(id)`, `game.jump(id)`, `game.systemOf(selection)`
- `game.world.fleets` and their `orders` are mock data for the gallery and test fixtures only; nothing moves them. Real ships are `ships.vessels` (see Ships below)
- `game.selection`: `{ kind: 'fleet' | 'body' | 'contact' | 'site' | 'ship' | 'base', id }` (`ship` is a vessel id, `base` an economy site id); set it with `select(kind, id)` from `#lib/ui/index.ts`, which also shows the Selection window
- `game.advance(seconds)`, `game.setStep(seconds)` (single-steps when paused), `game.run()`, `game.pause()`, `game.toggleRunning()`, `game.log(category, text, warn, { at, subject })` (an event files by its time; a `subject` makes it select that object when clicked)

While running, the loop advances `game.step` of game time per real second, ten ticks a second.

### Ship classes

There are no premade classes. `game/classes.svelte.ts` holds the one registry (`classes`, starts empty) of the `ShipDesign`s the player makes: `shipClasses()`, `shipClass(id)` (the drawable top-down spec, built once per design object), `classStats(id)`, `className(id)`. A ship keeps only its `classId`. The Ship classes screen edits the registry; Economy, the map and Intelligence read it and must cope with it being empty. The mock fleets still name classes that no longer exist, so `className` gives them `Unknown class` and the map draws them as markers. A screen that keeps a class in use (a yard tooled for it) registers `registerClassUse` so the designer will not delete it. `game/design.ts` is only the drawing geometry (`layout()`, `lengthOf()`); `gfx/ships/specs.ts` `SPECS` are art for the mock scenes, not classes.

### Ship design

`src/lib/game/shipdesign/` (import from `#lib/game/shipdesign/index.ts`) is pure TypeScript with no Svelte. A `ShipDesign` is `{ id, name, role, yard, parts: [{ component, count }], load, locked }`: `role` is one of `ROLES` (launcher, transfer, lander, capsule, freighter, probe), `yard` is `rocket_factory` (on Earth, so the ship must lift off from it) or `orbital_shipyard`, `load` is kilograms of each `PropellantKind`. Edit it only with the functions in `edit.ts` (`setCount`, `addPart`, `removePart`, `setLoad`, `rename`, `setRole`, `setYard`, `copyOf`, `lock`, `canLock`): each returns a new object, a locked design comes back unchanged, and tanks that were full stay full as parts change. A class that is locked can only be copied.

**Component figures** are the `design` record of each entry in `components.json`: `mass` kg (an engine takes it from `performance.mass`), `crew` needed aboard (a reactor or drive needs an operator unless some component `automates`, as avionics does; a capsule's own crew stays), `housing` berths, `stores` kg of consumables, `supports` crew a life support unit sustains, `power` kW drawn, `generates` kW made at 1 AU, `storage` kWh (a battery, or the `fuel_cell`: hydrogen and oxygen reactants with the stack, 500 kWh, milestone 1, estimated, which lets a capsule fly before any solar array or battery exists), `heat` kW of waste heat (defaults to `power`), `radiates` kW, `volume` m3 of tank, `propellants` (a tank holds them, an engine burns its one), `cargo` kg, `landing` and `reentry` kg a set of legs or a heat shield handles, `insulates`, plus `basis` (how the figure comes about), `source` (a URL where it is real) and `estimated`. Propellant kinds in `propellants.ts` give the bulk density in a tank, the materials of the mix and whether it is cryogenic; tank room is the volume shared between the kinds that tank accepts.

**`designStats(design, unlockedUpTo?)`** returns `lines` (count, mass, material cost per component), `dryMass`, `propellant` and `capacity` by kind, `payloadCapacity`, `loaded` (full tanks and bay) and `empty` (no payload) conditions each with `mass`, `deltaV` (through `shipDeltaV`), `acceleration` and `thrustToWeight` and `liftoff` on `earth`, `moon` and `mars` (sea-level thrust on Earth, `MIN_LIFTOFF_TWR`), `drives` and `main` (the drive with the most delta-v; engines of one propellant add up with a thrust-weighted Isp), `crew`, `berths`, `stores`, `endurance` days (5 kg a person a day without a life support unit, 1 with), `power` (made, used, engines, balance, storage), `heat` (produced, radiated with 0.5 kW a tonne passive, balance), `builtAt` (yards that can build every part), `cost` and `propellantCost` in materials, and `issues` with `errors` and `warnings`. A class can be locked only with no errors. Errors: no parts, a locked component, no engine, no tank for the engine's propellant, no propellant loaded, crew without berths or stores, power deficit (stored energy, a battery or a fuel cell, turns it into a warning that gives the hours it lasts), heat deficit, a yard that cannot build the parts, a lander without legs or overloading them, a return capsule without a heat shield or overloading it, a freighter without a cargo bay. Warnings: thrust too low to leave Earth alone from the rocket factory (a stage that rides a lower stage in a launch stack, so the stack checks it, not the design), load that does not fit, a throttled electric drive, no battery for an eclipse, a launcher short of the delta-v to reach low Earth orbit, a reactor beside the crew without a shield, cryogenic propellant without insulation on anything but a launcher, a lander too weak to hover on the Moon.

**For flight:** `flightShip(design, { propellant?, payload? })` returns what `planTrip` takes (`{ dryMass, payload, propellant, engine, powerAvailable }`) or `undefined` with no engine: `dryMass` includes the other propellants carried, `engine` is the main drive added up (`thrust`, `thrustSeaLevel` and `power` are totals, `count` is left out), `propellant` and `payload` default to the full propellant load and an empty bay and are clamped to what the design holds. `designSpec(design)` (`art.ts`) maps the components to the top-down generator's parts: engines to the stern (`big` for four or more or a nuclear or fusion drive), tanks, reactors, habitats, trusses and cargo bays to sections (a count of n gives `1 + floor(log2 n)` sections up to a cap), solar arrays, radiators, thrusters, legs and antennas to attachment slots, and a capsule, adapter or heat shield to the bow.

**The screen** (`screens/classes/`) edits the registry live with no save step, in the mockup's three columns. Left, `Palette`: every component as a `cmp` tile grouped by kind (`KIND_NAMES`), with its name and a key figure (Isp for an engine, mass otherwise), `×n` when the open class holds it, a tooltip of its figures (`factList`), and a locked one dimmed, disabled and marked `after <milestone>`, its tooltip naming the milestone it waits for; clicking a tile adds one, and with no class open starts one with it. Middle, the drawing (the real top-down generator through `drawDesign`, with its length and beam) above the `Class` panel: New, Copy, Lock and Delete in its title bar, the class list (`#classList`, one button per saved class), the name (`#clsName`), role and built-at selects, and `Strip`, one tile per component with minus, a count input and plus. Right, `Stats`: the eight dense `Stat` tiles of the mockup (mass, delta-v, thrust to weight, thrust, crew, power, propellant, heat), the propellant load by kind with Fill and the payload shown (`Load`; the payload defaults to the bay and is lowered, never raised, since `flightShip` clamps it), `Flags` (every issue of `designStats` as an `error`, `warning` or `ok` flag with `data-issue`), the build cost as material icons, and a second group of tiles for the figures the first eight leave out (delta-v empty, bay capacity, thrust to weight on Earth, the Moon and Mars, acceleration, life support days, where it can be built). Every figure is built in `figures.ts` from `designStats`, and each tile sits in a `data-stat` cell for the tests. A locked class disables every edit and can only be copied. `?screen=classes&new=stage` and `&new=crewed` open a ready design, and `&reached=<n>` marks milestones 1 to n reached, for tests.

### Drawing ships

Every ship outside the System map is drawn top-down from its class design by `gfx/topdown/`, the port of `mockup/scenes/ships.js`. `gfx/ships/specs.ts` holds the shared vocabulary: the part keys (`CORE_KEYS`, `STERN_KEYS`, `BOW_KEYS`, `ATTACHMENT_KEYS`), their names (`PNAME`) the shipped `SPECS` (art for the mock scenes) and `designSpec()` in `game/shipdesign/art.ts`, which draws a class from its components. A design is laid stern to bow in units of `METRES_PER_UNIT` (5 m); `design.ts` `layout()` and `lengthOf()` read the same geometry, so a stat length is the drawn length.

Each part is built into a heightmap, material, component and emissive map once per class object and detail level (`LODS`, 0.375 to 12 px per 5 m) and cached on the class object, so an edited class (a new object) gets new sprites and an unchanged one is never rebuilt. A scale between two levels draws the next level up, scaled down. Each part and each hardpoint is its own component with a `kind` (system), a `name`, its `part` index in `layout()` order and its `slot`.

The API, from `#lib/gfx/index.ts` or `#lib/gfx/topdown/index.ts`, takes any `Pixels` (`w`, `h`, `d`, `px`; an `FB` is one) and screen positions, so a caller draws many ships from its own list of positions:

- `drawShip(fb, cls, { x, y, angle, pxPerMetre, sun?, frame?, livery?, thrust?, damage?, aim?, swap?, systems?, highlight?, dead?, cut?, build?, ghost?, clipX?, charging? })` draws true scale at the detail level for `pxPerMetre`, with drive plumes, turrets turned by `aim` (radians relative to the hull, one per `shipMounts` entry) and lighting from `sun` (screen angle towards the light; the mockup's default when left out). Returns `{ lod, scale, culled }`.
- `drawShipIcon(fb, cls, x, y, angle, sizePx, view?)` draws a fixed-size sprite, whatever the class length.
- `fitShip(cls, w, h, pad?, plumeRoom?)` gives the centre and `pxPerMetre` that fit a class into a box.
- `shipLengthMetres(cls)`, `shipBeamMetres(cls)`, `shipMounts(cls)` (metres from the ship centre, x towards the bow), `shipComponents(cls)`, `pickShip(cls, view, sx, sy)`, `nearestHull(cls, x, y)`, `detailLevel(pxPerMetre)`, `liveryOf(cls)`.
- `new ShipDamage()` holds hits in metres from the centre (`hit(x, y, radius, severity)`); pass it as `damage` and it is mapped onto each detail level once.
- `silhouette(fb, cls, view)` is the red treatment for an unidentified class.
- `drawStation(fb, 'core' | 'ring', view)`, `drawProp(fb, kind, view)` and `drawCraft(fb, 'fighter' | 'shuttle', view)` draw the mockup's stations, props and small craft.

`frame` is the animation counter for blinking lights, plumes and charging guns; screens pass three per frame-bus tick, as the mockup ran at 30 frames a second. Drawing cost grows with the pixels a ship covers, about 90 ns each: draw small ships with `drawShipIcon` rather than at a true scale that covers the screen many times over.

### Drawing small bodies

Asteroids and comet nuclei are not drawn by the sphere renderer. `smallBodyOf(body)` (`game/smallBodies.ts`) says which `Body` is small: an asteroid record, or a body whose `facts.kind` is `Comet`; the Moon and Mercury are `rock` and keep their sphere, so never branch on the planet type. `gfx/bodies/small/` (import from `#lib/gfx/bodies/small/index.ts`) draws one: `smallBody(info)` (`id`, `name`, `type`, `diameter` in km) picks a shape family from the name (`catalogue.ts` `NAMED`: Bennu, Ryugu and Didymos as spinning tops, Itokawa and Arrokoth as contact binaries, Eros and Ida as peanuts, Apophis and Gaspra elongated, Kleopatra a dog bone, Mathilde, Lutetia and Psyche lumpy, Vesta, Ceres, Pallas and Hygiea nearly round) and otherwise from diameter and a hash of the id; a type it does not know is drawn stony and `comet` gets a two-lobed or lumpy nucleus with a dithered coma and tail drawn into the frame behind it. A shape is a `ShapeSpec` (`shape.ts`): lobes (ellipsoids, or a superellipsoid for a top) joined by a smooth maximum, low-frequency lumps, an equatorial ridge, and craters, boulders, basins and bright spots as relief on a radius function of direction, normalised to a mean radius of 1. `field.ts` bakes that function once per shape and detail class (`fieldClass`: 32, 64, 128 or 192 texels a cube face, keeping only craters and boulders that cover at least a couple of pixels at that size) into a padded float cube with a tone channel and an analytic hull of the lobes. `render.ts` sphere-traces each pixel against the hull and field, takes the normal from the field, and shades with the planets' light, four dithered levels and palette by type (carbonaceous dark and low contrast, stony brown-grey, metallic cool with a sheen). A rendered frame is cached as an RGBA sprite by body, radius and spin frame (`SPIN_FRAMES` 48 a turn, within a 96 MB budget); a draw is a blit, and a radius above 110 paints straight into the frame buffer. Spin is `spinStep(t)`, one frame every `SPIN_TICKS` ticks, with a phase, direction and axis tilt per body; above `SPIN_MAX_RADIUS` the body does not turn. The map includes the step in its frame-cache key only while a turning small body is on screen. Below the map's marker size an asteroid is still the plus mark. `drawSmallBody(fb, body, cx, cy, radius, step)` is the one call; the radius is the mean radius in pixels and `smallReach(body)` the largest extent as a multiple of it. It is used by the map (`drawMap.ts`), the Selection picture, and the Economy site panel and site list. `/dev/bodies` (gallery build) shows every family, each named, at three sizes, and `small.test.ts` checks determinism, every named shape at every size and that nothing renders empty. `?scenario=belt&asteroid=bennu` founds a miner site on an asteroid for the layout states.

### Top bar chips

`game.status` is evaluated from sources a screen registers with `registerStatus(id, () => ({ icon, value, title, warn? }))` from its `system.ts`; the ids and their order are `STATUS_IDS`. Economy owns all six: people, food against need, power balance, compute, the scarcest material and milestones reached. Read the state the chip describes; never store a chip's value.

### Game data

The economy runs on JSON in `src/lib/game/data/`, so that a Rust simulation can read the same files later. `#lib/game/data/index.ts` loads them and exports the records (`materials`, `recipes`, `buildings`, `shipComponents`, `milestones`), lookups by id (`material(id)`, `building(id)`, ...), and the derived graphs: `recipesProducing`, `recipesConsuming`, `recipesAt`, `materialSites` (where a material is extracted and where it can be made), `unlockedAt`, and `reach`, which computes what exists from extraction alone up to a milestone, on the thin path or the whole set, or on one site.

| Folder or file                       | Holds                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------- |
| `materials/<category>.json`          | one small record per material; a category that outgrows about 400 lines gets `<category>-<part>.json`   |
| `recipes/<group>.json`               | a building turns `inputs` into `outputs`, each a map of material id to amount                           |
| `buildings/<kind>.json`              | where it stands, what it costs, who works it; extractors name the materials they work through `sources` |
| `components.json`, `milestones.json` | ship components; the 29 gates from present-day Earth to a stabilised jump point                         |
| `regions/<group>.json`               | regions of a body with deposits and grades (see Regions below)                                          |
| `asteroids.json`                     | 59 real asteroids: orbit, size, mass, type (see Asteroids below)                                        |

Ids are `snake_case` and unique across materials, buildings, components and recipes. Amounts are kg unless the material has a `unit` (`cu` compute, `model` trained model). A recipe's `power` is kW while it runs, `hours` is the batch time, and `generates` is kW produced by a generator.

- **A material** is one record in the file of its category. `sources` lists where it is mined or collected: `{ body, how, building }`, with a `body` from `types.ts`, and a `building` of kind `extraction` that stands on that body. A material with no `sources` must be the output of a recipe. `tier` is `P` proven, `E` engineering-plausible, `S` speculative. `source` is a working URL.
- **A recipe** is one record in the file for its building. `milestone` is when it unlocks and may not precede its building's. `estimated: false` means the ratio follows a balanced reaction or a standard composition that `reaction` states and `source` cites; the tests then check the mass balance to one percent. Everything else is `estimated: true`, and no recipe may create mass. `power` and `hours` are placeholders everywhere until the economy is tuned.
- **A milestone** lists in `needs` the materials, buildings and components that must be producible when it is reached, using what milestones up to and including it unlock. `requires` names earlier milestones only.
- **The thin path** is `thin: true` on a record. Thin recipes, buildings and components may use only thin materials, every milestone's `needs` must be thin, and `reach({ thinOnly: true })` must reach all of them in order. Buildings with `start: true` exist on Earth at the start and are not paid for.
- Politics never restricts supply; scarcity comes from physics, geology and industry only.

`src/lib/game/data/data.test.ts` is the gate: unique ids, known references, every material extractable or produced, mass balance, the thin path closing on itself, every milestone 1 to 29 reachable in order, and no material, building, component or recipe stranded by a cycle. Add data, then run `pnpm exec vitest run src/lib/game/data` until it is green.

### Flight planning

`src/lib/game/flight/` is the movement rule of #8 as pure functions: SI units (metres, seconds, kilograms, m/s), float64, no Svelte, no globals, nothing wired into the game loop yet. Import from `#lib/game/flight/index.ts`. Time is game seconds (`game.elapsed`). It takes bodies as arguments (`FlightBody`: `gm`, `radius`, `orbit`, `angle`, `angularSpeed`, optional `parent`, `lowOrbitAltitude`, `atmosphere`), so it does not import the mock world; `reference.ts` holds real Sun, Earth, Moon, Mars and Jupiter constants for tests.

- **Engines**: `components.json` gives each propulsion component a `performance` record (`isp` s, `thrust` N vacuum, `thrustSeaLevel`, `mass` kg, `power` kW, `basis` flown, ground-tested or design-study, `source` URL). A `Ship` is `{ dryMass, payload, propellant, engine, count?, powerAvailable? }`; an electric engine's thrust is scaled by `powerAvailable / power` when that is given.
- **Rocket equation** (`rocket.ts`): `propellantForDv`, `dvFromMasses`, `shipDeltaV`, `massAfterBurn`, `burnTime`, `meanAcceleration`, `legBudget(ship, [dv1, dv2])` for out-and-back, `roundTripFeasible`.
- **Wells** (`wells.ts`): `surfaceToOrbit`, `orbitToSurface({ aero })`, `escapeFromOrbit(gm, r, vInf)` and `captureIntoOrbit(...)` with the Oberth effect, `lowOrbitRadius`, `circularSpeed`, `orbitalPeriod`.
- **Transfers** (`kepler.ts`, `line.ts`, `spiral.ts`): `hohmann`, `synodicPeriod`, `crossingTransfer` (departure burn tangential, arrival crossing the target orbit; reduces to Hohmann), `brachistochroneTime`, `burnFlipBurn`, `burnCoastBurn`, `solveLine` (moving target), `lineThresholdAcceleration`.
- **Planner**: `planTrip({ from, to, departAfter, ship, system, aerobrake? })` returns `{ options, reasons }`. A `Place` is `{ kind: 'surface', body }`, `{ kind: 'orbit', body, altitude? }` or `{ kind: 'point', id, primary?, orbit, angle, angularSpeed? }` (a jump point or station at fixed elements). Each `TripOption` has `profile` (`cheapest`, `balanced`, `fastest`), `model`, `departure`, `window`, `arrival`, `duration`, `dv`, `propellant`, `propellantLeft`, `canStop`, `canReturn`, `returnDv`, `aerobraked`, `maneuvers` (kind, mode, dv, duration, start) and `stamps`. `reasons` carries a code (`delta-v`, `thrust-surface`, `thrust-landing`, `no-path`, `same-place`, `unknown-body`) with `need` and `have`; when a ship can leave but not stop, one option with `canStop: false` comes with the `delta-v` reason.
- **Ship state**: `positionAt(option, t)` gives `pos`, `vel` (system frame), `phase` (`parked`, `departing`, `accelerating`, `coasting`, `decelerating`, `transfer`, `arriving`, `arrived`), `thrusting`. It is a function of absolute `t` only, so a 30-day step and thirty 1-day steps give the same position. `eventsOf(option)` lists burn starts and ends, the flip and the arrival.

Approximations, all deliberate:

- **Common primary.** A trip is planned around the deepest body both places orbit (Sun for planets, a planet for its moons). Moon-to-planet legs climb out stage by stage: escape the moon to zero excess speed, then escape the planet from the moon's orbit radius. Circular coplanar orbits only, prograde, no gravity assists, patched conics.
- **Ascent and landing.** Ideal energy cost `sqrt(2 gm (1/R - 1/(2 r)))` times `1 + 0.085` (gravity loss calibrated on the Moon's 1.87 km/s) plus the body's `atmosphere.ascentLoss` (calibrated net of rotation so Earth gives 9.4 km/s). Lift-off needs thrust-to-weight 1.2 on sea-level thrust; landing needs 1.0 at the final mass unless the body's air does it (`landingDv`). Aerobraking is `captureIntoOrbit` with `residualDv` instead of the burn, only below `aerobrake.maxVInf`, and only when `aerobrake: true`.
- **Orbit model (impulsive).** Burns happen at the periapsis of the parking orbit as up to 24 passes of at most 30 degrees of arc each, with a finite-burn loss of `arc^2 / 8` per pass (velocity-aligned thrust). More passes than that makes the leg a continuous spiral costing `vc + vInf`. If the thrusting at a planet spans more than 30 degrees of that planet's orbit, the whole trip becomes a spiral.
- **Spiral model.** Edelbaum tangential thrust between circular orbits, `|vc1 - vc2|`; position is `r = gm / v^2` with the swept angle integrated numerically. Valid while the acceleration is well below local gravity; the arrival velocity then has a radial part of about `2 a / g` of the circular speed (measured 9 percent for two NEXT thrusters on a 5.5-tonne ship going to Mars, 37 percent for eight). `TripOption.approximate` is true when `a / g` at the outer orbit exceeds 0.1.
- **Windows.** The target must lead the origin by the angle that makes the ship meet it: `sweep - omega_target * T`. Windows repeat at the synodic period. A ship parked at a planet departs from any phase of its parking orbit; the wait of up to one parking period is not added.
- **Fast transfers.** `crossingTransfer` raises the departure burn above Hohmann: faster, costlier, arriving across the target's orbit instead of tangent. It is only used while burns take at most 25 percent of the flight (impulsive assumption).
- **Straight-line model.** The primary's gravity is ignored. Thrust is constant at the mass-averaged acceleration of the burn, found by fixed point with the rocket equation; with a delta-v budget below the full burn it is burn-coast-burn. The target moves, so the flight time is solved by iterating the arrival point; arrival matches the target's velocity. Used only when `g(r_closest) * T / (a * t1) <= 0.05` (equivalently `a >= 2 g / 0.05` for a full burn, `lineThresholdAcceleration`: 0.24 m/s2 at 1 AU for the Sun), and the straight path stays outside the primary. Integrated under the Sun's gravity at the threshold the miss is 3.8 percent of the distance; at ten times the threshold it is 0.4 percent, at a tenth it is 30 percent (`line.test.ts`). The planner delays a straight-line departure up to one synodic period to clear the Sun.
- **Why the models are not compared at a boundary.** Hohmann minimises delta-v and the straight line minimises time, so for one ship they differ by orders of magnitude in both (259 days at 5.6 km/s against days at hundreds of km/s). What the tests check is each model against numerical integration of its own physics, and that a very fast crossing orbit reduces to a straight coast.
- **Profiles.** `cheapest` is Hohmann (or the spiral); `fastest` spends the ship's whole delta-v on whichever of the crossing family and the straight line arrives first; `balanced` is the same at the geometric mean of the two delta-v. `canReturn` plans the return from the arrival time with the propellant left and without aerobraking.
- **Positions.** The ship follows the primary-centred path from the origin level's centre to the target level's centre; during local burns it is on the place's own parking ring. Jumps between the two are at most a parking radius.

### The economy

`src/lib/game/economy/` simulates the data above. It is pure TypeScript plus one `.svelte.ts` for the live state, and it imports no screen; `screens/economy/system.ts` registers it as the `economy` system and owns the chips. `economy` (from `#lib/game/economy/index.ts`) is the one `Economy`: `sites`, `done` (milestone numbers reached), `running` programmes, `elapsed` and a mass `ledger`. Change it only through the actions in `actions.ts` and `programmes.ts`, then call `touch()`, which drops the cached `flowsOf(site)` that every screen reads.

- **A site** is a place with a stockpile (`stock`, kg or the material's unit), building `groups`, a construction `queue`, `population`, a workforce share and a `gridKw`. Its `body` is a data `Body`, which decides what can stand and be extracted there, and `worldBody` is the map body. Earth is the only site; a station, the Moon or an asteroid is another `Site` in `economy.sites`, and nothing else changes.
- **A group** is `count` buildings of one type running one `process`: a recipe, or `extract:<material>` for a material whose `sources` name that building on that body (`EXTRACT_KG_PER_HOUR` each, a placeholder). A recipe input its own building extracts where it stands (air at an air separation plant) is drawn from the environment. A group with no process is idle; one switched off runs at nothing. `assign(eco, site, group, process, count)` moves some or all of a group to another unlocked process.
- **Rates.** `siteFlows(eco, site)` gives every group a share of full rate: capped by workers (population times workforce share, shared out in proportion), then scaled down in proportion wherever an input has no stock and its consumers want more than its producers make. Power (`POWER`) and compute are never stockpiled, so they always balance this way: the grid plus generators against demand, data centres against recipes, builds and programmes. Food is counted in calories: every food material (`category: food`) has `kcalPerKg` with `kcalSource` and `kcalBasis` (wheat 3,270, potato 770, soybean 4,460, leafy greens 150, meat 2,200 estimated, single-cell protein 3,500 estimated, food ration 2,800 estimated: the ration is one packaged kilogram a person a day for the reference diet), and a person needs `kcalPerPersonDay` (2,800, the FAO, WHO and UNU figure for a moderately active man of 18 to 30; a `Site` carries it, new sites take Earth's). People eat from surplus first and stores second, shared out between foods by calories, so `flows.food` (`demand`, `made`, `eaten` in kcal an hour, `eatenBy` and `madeBy` per food, `cover`) is in calories while `flows.eaten`, `eatenMass` and the ledger stay in kilograms; cargo, stock and programme bills stay in kilograms too (`kcalOf(id)` converts). Population grows `growthPerYear` only while the calorie need is met and shrinks by `STARVE_PER_YEAR` times the shortfall otherwise. The Summary tab shows calories made by food as a bar against the need, each food's share of what is eaten, and a tile per food; the top bar's food chip is calories made against needed.
- **Time.** `advanceEconomy(eco, seconds, log)` integrates in segments that end at each game day, when a stock runs out, when a build finishes and when a programme finishes, so a 30-day step gives the same totals as thirty one-day steps. The ledger counts kilograms extracted, eaten, built, spent on programmes and lost in recipes; the stock change always equals extracted less the rest.
- **Construction** builds the first `BUILD_SLOTS` unpaused orders in queue order, spending each building's cost evenly over `buildHours` (placeholder: ten days plus two days a tonne); a short material slows it and is named on the order. A finished building joins the group with the same building and recipe.
- **Programmes.** Records tagged with milestone `m` unlock once every non-optional milestone below `m` is done (`unlockedUpTo`), which is the order `reach({ upTo })` checks. A milestone can start when its `requires` are done, its buildings stand, a builder for its parts stands and its bill is in stock; starting spends the bill. The bill (50 t times the milestone number of each needed material, plus one of each needed part), the length (60 days plus 30 a step, longer for engineering and speculative tiers) and the compute (from milestone 6) are placeholders in `programmes.ts`.
- **What a milestone needs to stand somewhere.** `needs.sites` in `milestones.json` is a list of `SiteNeed` (`label`, `world` or `body` type, `place`, `region`, `buildings`, `people`, `fed`, `stock`) and `missingFor` reports `{ kind: 'site', label }` until some site meets each (`economy/needs.ts`: `siteNeedMet`, `siteNeedMissing`; `fed` is a site with people and no food alert). They are: 6 a crewed outpost on the Moon, 7 a fission reactor on the Moon, 8 an ice mine in the south polar region, 11 a greenhouse on the Moon with four people who are fed, 12 an ice mine, electrolysis plant and liquefaction plant on the Moon, 15 a sample on Earth (0.1 kg of carbonaceous chondrite, which Earth cannot make), 16 a miner on the surface of a carbonaceous asteroid, 17 on a metallic one. Milestones 18 to 29 add counters a site keeps, since a building standing says nothing about what it has done: `Site.built` (ships a yard has finished), `Site.ran` (building-hours a group worked, weighted by its share, kept under the building id and the process id) and `Site.made` (kilograms of each material produced there, extraction included); `economy.flown` counts the trips ended by each drive component. A `SiteNeed` reads them with `built`, `ran`, `made` and `flown` (the last is not about a site). They are: 18 an orbital shipyard that has built a ship, 19 a semiconductor and a solar cell fab in orbit with the fab run 24 hours, 20 a solar power station in orbit run 24 hours, 22 a fusion plant that ran `d_t_fusion_power` 24 hours, 23 1,000 kg of helium-3 made in the lunar maria, 24 a ship that has flown on a fusion drive, 25 a scoop standing at a gas or ice giant that made 1,000 kg of helium-3, 26 5,000 kg of carbon nanotube fibre made in orbit beside an orbital shipyard, 27 600 kg of room-temperature superconductor made, 28 an exotic matter facility in orbit that made 0.01 kg, 29 a stabiliser standing at the jump point. All thresholds are placeholders. Milestone 21 (Mars in-situ resources, optional) has no site need and no Mars outpost is played: the player runs its programme only, since the ice mine and the oxygen plant stand on the Moon and Earth makes the methane. A site need adds no building or material to `needs`, so `reach` and the thin path are unchanged. The Research screen's programme card lists each as a row with whether it is met. A need with a `made` or `ran` threshold also shows how far the best matching site has got, as a share (`siteNeedProgress`).
- **What a programme is paid in.** `programmeBill` leaves out any material Earth cannot make (`earthMakes`, `reach({ site: 'earth' })`): programmes run at the home site, where the compute is, and a bill of 400 t of lunar regolith, 800 t of carbonaceous chondrite or 850 t of asteroid steel cannot be delivered there; the site needs above test those instead. Everything Earth makes is paid as before, except where a milestone gives `needs.bill`, an amount in kilograms for one material in place of the 50 t times the milestone number: tritium, deuterium and lithium-6 come at 1 kg a day or 0.1 kg an hour from a plant, so milestones 22 and 25 ask for 20 kg, 200 kg and 200 kg. A component's builder (`builtAt`) counts when it stands at any site, as a building need does, so the fusion drive, which only an orbital shipyard builds, is satisfied by the shipyard in orbit.
- **The Research screen** (`screens/research/`) is where a programme is started. A stat strip (milestones reached, programmes running and when the next finishes, ready of open, compute, buildings and parts open) sits over three tabs, `?rtab=tree`, `programmes` and `unlocks`, and the programme card on the right. `Tree` lays the milestones out in columns by depth (`chain.ts`) as opaque `node` tiles with a short name (`names.ts`) and an icon picked from what the milestone needs (`milestoneIcon`), with lines drawn from the measured tile size: amber from a done milestone, dashed from one not done; selecting one outlines what it needs in amber and what it opens in teal; the tree keeps a height of 440 px and shrinks its tiles, hiding their pictures below 84 px, on a short window. `ProgrammeList` groups the milestones as running, ready, waiting, locked and done, with how much of the bill is in store. `UnlockList` shows what each milestone opens (`openedBy`: buildings, parts and the materials no earlier recipe makes). `ProgrammeCard` is the same card on every tab: header with the status, then length, tier and compute, then Start (`#programmeStart`, enabled only when `programmeStatus` is `ready`) or the progress, with the first missing thing beside it, then the bill as have and need, what must stand (buildings and parts as yes or no boxes) and each site need as a row (`#siteNeeds`), the milestones it needs and any earlier ones still open, and what it unlocks. `checkFor` in `programme.ts` collects every blocker and `programme.test.ts` checks its count against `missingFor`, so the card cannot show less than the game checks. A programme is started from this screen.
- **Earth at the start** is `src/lib/game/data/earth.json`: population, workforce share, kcal a person a day, growth, grid, stock days and the groups. Its `sizing` block states the rule the counts follow: ranches (`ranch_meat`: 3 kg of cereal and soybean feed and a tonne of water for a tonne of meat, from the published figure of 2.8 to 3.2 kg of human-edible feed a kilogram of boneless meat; `estimated` water) make meat for about 10% of the calories, about 380 Mt a year against about 360 Mt in the world today, and farmland feeds the rest of the population with a 5% surplus in calories, end products run at present-day world output, every other group feeds its consumers plus 10%, the grid covers start demand with about 15% to spare, and stocks start at 90 days of production. Change a count and keep that rule, or change the rule there.
- `?scenario=famine` halves Earth's farmland and empties its food stores at load, for tests.

### Regions, survey and asteroids

**Regions** (#15) are `data/regions/*.json` records `{ id, world, body, name, kind, known?, deposits: [{ material, grade }], basis, source, estimated }`, loaded by `data/regions.ts` (`regions`, `regionsOf(world)`, `atmosphereOf(world)`, `region(id)`, `depositGrade(world, regionId, material)`, `bodyTypeOf(world)`, `typeHolds`). `world` is a map body id and `body` its data type (`WORLD_BODIES` maps luna to `moon`, europa, ganymede, callisto and enceladus to `icy-moon`, the giants to `gas-giant` and `ice-giant`; an asteroid takes its type from `ASTEROID_BODY`). A `ground` region is a named place a surface site can stand in; an `atmosphere` record is body-wide and reaches every region of its body (Mars, Venus, the four giants, Titan). Earth has no regions: `depositGrade('earth', ...)` is 1 and it stays one rich site. A deposit is a material that some building extracts on that body type (`data.test.ts` checks it, and that every source on a mapped body type is held by some region, so `reach` still closes: it takes a source as open only where a region of that type holds the material, `comet` having no bodies yet).

- **Grade** is a relative richness index from `GRADE_MIN` 0.05 to `GRADE_MAX` 4: 1 is the nominal 1,000 kg an hour of the extractor, and a deposit of grade 2 yields twice that for the same power. Every region is `estimated: true`; its `basis` gives the real figures (LCROSS 5.6 percent ice at Cabeus, Lunar Prospector thorium, MESSENGER sulfur, Dawn ice and organics on Ceres) the grades are scaled from, and `source` a URL.
- **Extraction by region.** `Site.region` is the region id for a surface site off Earth and `null` for Earth and for an orbital site. `gradeAt(site, material)` is the region's grade, the atmosphere's for an atmospheric source, 1 on Earth and `undefined` where the region lacks the material or the site is in orbit (orbit extracts nothing from the ground). `unlockedProcesses` and `firstBuildings` list only processes whose materials the region holds, so an ice mine cannot stand in the maria; a group whose region cannot supply its material runs at nothing with limit `deposit`. An `extract:` group's outputs and extracted mass are multiplied by its grade and the `GroupActor` carries `grade`; the grade pill on a Production card and the Summary tab's Region block show it. A site is unique per body, place and region: `newSite` takes `region`, the first surface site keeps the body id and later ones take the region id, so a second site may stand in another region of one body.
- **Depletion applies to asteroids only.** All extraction at a surface site on an asteroid draws down `economy.mined[body]` against the body's whole mass (`remainingMass`); the economy ends the segment at the moment the mass runs out, the group's limit becomes `depleted`, `economy.exhausted` lists the body and an event is logged. Ceres follows the same rule but its mass makes the limit unreachable; planets and moons are never depleted.
- **Survey.** `game/survey.svelte.ts` holds `survey.levels` (world id to 0 or 1; `resetSurvey()`). Every region is unknown until its body is surveyed except where the record says `known: true`: the Moon (all four regions, because Lunar Prospector, Clementine, Chandrayaan-1, LRO and LCROSS mapped it from orbit and sample return covers its main rock types) and every atmosphere (spectroscopy and probes). Mars, Mercury, Ceres, the asteroids and the icy moons start unknown. The order `survey` (`{ type: 'survey', body }`) needs a ship whose design carries the `survey_suite` component (`surveys: true` in its design, milestone 5, estimated, sized after the Lunar Reconnaissance Orbiter payload), in orbit of the body (free in orbit or docked at its orbital site), for `surveyDays(world)` days (`SURVEY_DAYS_PLANET` 60, `SURVEY_DAYS_SMALL_BODY` 14, placeholders); then `completeSurvey` marks the body done, the regions appear and the log says so. A body without ground regions (Venus, the giants) has nothing to survey. Grades are shown to a first precision: `gradeView` gives a range `low to high` that holds the true grade, wide by `SURVEY_ERROR` 0.3, stable for a region and material; a site's own Economy view shows the exact grade.
- **Founding.** `foundOptions(v, region)`, `foundRegions(v)`, `needsRegion(v)` and `foundSite(game, v, building, region)`: a ship on the ground of a body with ground regions must name a known region with no site yet, and only buildings that can work in it are offered. A `land` order and a trip destination may carry `region`; a vessel that lands in a region with a site arrives at that site.

**Asteroids** (#13) are `data/asteroids.json` records from JPL's small-body database (`https://ssd.jpl.nasa.gov/tools/sbdb_lookup.html`): `{ id, number, name, type, spectral?, a, e, diameter, mass, massEstimated?, source }` with `a` in AU, `diameter` in km, `mass` in kg. Seven near-Earth asteroids (Apophis, Aten, Bennu, Ryugu, Itokawa, Eros, Didymos) and Ceres plus 51 main-belt bodies (Vesta, Pallas, Hygiea, Psyche, Kalliope and others); `type` is carbonaceous, stony or metallic and maps to `asteroid-c`, `asteroid-s`, `asteroid-m`. `type` and class come from the Tholen or SMASS class; X-types follow Tholen (M metallic, P carbonaceous). No near-Earth asteroid is metallic here: Amun, once taken for the metal one, is now classed D or C by its infrared spectrum, and 1986 DA's class is not given by the database. `mass` is from the database GM where it is given with three digits or more, and otherwise `massEstimated` from the diameter and a bulk density of 1.4 (carbonaceous), 2.7 (stony) or 4.0 (metallic) g per cu cm. `game/asteroids.ts` turns a record into a map `Body` (circular orbit at `a`, `angularSpeed` from Kepler's third law, `angle` from a hash because the real phase is not modelled: **estimated**), `isNearEarth` is perihelion under 1.3 AU. Every asteroid has one region `<id>-body` generated from the template for its type in `regions/belt.json` (carbonaceous: chondrite, water, carbon, phosphorus; stony: chondrite, iron, Fe-Ni metal, nickel, silicon; metallic: Fe-Ni metal, iron, nickel, cobalt, platinum group and gold); Ceres has three regions of its own. The map's decorative belt dots remain as the uncatalogued mass.

### Ships, launches, sites and supply

`src/lib/game/ships/` (import from `#lib/game/ships/index.ts`) holds the ships the player owns. `ships` (a `$state`) has `vessels`, `launches` and counters; `resetShips()` clears it. It reads `classes` (designs), `economy` (stock, sites) and `flight/` (trips), and a vessel is not a mock `Fleet`. The `economy` system (`screens/economy/system.ts`) calls `advanceShips(game, dt)` after the economy, so a vessel built that tick appears in the same step.

- **Build.** `orderShips(site, designId, n)` queues a locked design with no errors at a site that has its yard (`rocket_factory` on Earth; `orbital_shipyard` is milestone 18). Components are folded into the ship's cost: the order spends `designStats(design).cost` evenly over its build time, never a separate component build. A yard group builds one ship at a time, so the number of yards standing is the number of ships in progress. A short material slows the order and is named on it (`stalled`); `moveShipOrder`, `pauseShipOrder` and `removeShipOrder` reorder it. A finished ship is delivered to `economy.delivered` and becomes a vessel at that site with empty tanks and an empty hold. **Placeholder, estimated:** build time is `SHIP_BASE_DAYS` (2) plus `SHIP_DAYS_PER_TONNE` (0.5 a tonne of dry mass); no workers or power are drawn.
- **A vessel** is `{ id, name, design, at, trip, propellant, cargo, crew, orders, run, progress, blocked }`. `at` is `{ kind: 'site', site }` (docked or landed at an economy site), `{ kind: 'orbit', body, angle }` (free in low orbit) or `{ kind: 'surface', body }` (landed with no site). `propellant` is kilograms by `PropellantKind`, `cargo` kilograms by material, `crew` people taken from a site's population. `vesselShip(v)` is what `planTrip` takes (the main drive, the cargo as payload, the other propellants as dead mass).
- **Launch.** `planStack(game, site, { stages, payload })` and `launch(...)` take stage ships (first stage first) that stand at a site with a `launch_site` building and a free pad. Each stage is topped up to its design `load` from the site's stock by the propellant's mix (a short material is a reason). The stack's delta-v is computed stage by stage with the rocket equation, each stage lifting everything above it; the first stage whose cumulative delta-v covers `surfaceToOrbit(body)` is the one that reaches orbit, burns only what is needed and keeps the rest; the stages above it are carried to orbit as ships. Lift-off thrust to weight is checked on the first stage only (sea-level thrust on a body with air, `MIN_LIFTOFF_TWR`). The payload is nothing, cargo (kilograms from stock into the top stage's cargo bays, so it needs bays) or a ship at the site. A stack short of orbit or of thrust is refused with the numbers. A stage that is separated and has landing legs rated for its mass returns to the pad with empty tanks (`returns`); any other separated stage is destroyed. The stage that reaches orbit becomes a vessel in orbit with its leftover propellant, cargo and crew. `payloadCeiling` is the most payload a stack lifts. Launch sites have a launch rate: each `launch_site` building takes one launch per `PAD_TURNAROUND_DAYS` (`site.launches` holds when each pad is free again). **Placeholders, estimated:** a returning stage holds back `RETURN_RESERVE` (7 percent) of its propellant for the return and burns it; `PAD_TURNAROUND_DAYS` is 4; the launch is instant in game time and the ship arrives at orbit angle 0. **Known value:** a stack of a nine-engine kerolox stage (20 tanks, one leg set) under a one-engine, five-tank stage reaches low Earth orbit with 18.8 t expended and 14.7 t reused against Falcon 9's 22.8 t and 17.5 t (`staging.test.ts`); the computed reused to expended ratio is 0.78 against the real 0.77.
- **Landing and ascent from the same body** (`hop.ts`): the planner has no path between a body's orbit and its own surface, so a `land` order from orbit of that body (or docked at its orbital site) is a descent of `orbitToSurface` delta-v and a `fly` order from its surface or a surface site there is an ascent of `surfaceToOrbit`, each an hour (`HOP_SECONDS`, placeholder), checked for delta-v and thrust to weight (1.0 landing, 1.2 lift-off) and burning propellant. The flight library's own formulas make this almost free on a small body: 0.19 m/s on Bennu, 9.7 m/s on Eros, about 315 m/s on Vesta, 430 m/s on Ceres, 1.87 km/s on the Moon.
- **The flight model covers every map body with a reference**: Mercury, Venus, Mars, the giants, Io, Europa, Ganymede, Callisto, Titan, Enceladus and every asteroid (`gm` from the record's mass, a parking orbit at `min(100 km, radius)`). Venus and the giants cannot be landed on (`LANDABLE`); Venus's and Titan's atmosphere constants are placeholders.
- **Trips.** `planVessel(game, v, destination)` calls `planTrip` from the vessel's place with the game's own bodies (`flightSystem(game)` turns the world bodies earth, luna, mars and jupiter into `FlightBody`s with the reference constants and the world's orbits and phases, so a trip and the map share one set of positions at `game.elapsed`). It returns the options that can stop (window, duration, delta-v, propellant, propellant left, whether it can return) or the reasons it cannot go in words. A ship leaves a surface site that has a launch site and air by launch stack only. `commitTrip` takes the propellant at once and `vesselState(game, v)` follows `positionAt`, so a 30 day step and thirty one day steps give the same position and arrival. A landing needs legs rated for the ship, or a heat shield rated for it on a body with air.
- **The jump point** is the `JumpPoint` of the system (`game.jump(id)`, `surveyed`, `stable`). The flight model gets it as a fixed `point` place (`jumpPlace`, static at the map position, so a ship matches rest there); a vessel at it is `{ kind: 'orbit', body: <jump id> }`, and `fly` takes the id as its body. A `survey` order at the point (`JUMP_SURVEY_DAYS` 30, placeholder) needs a ship with a survey instrument and marks it surveyed. `foundSite` at the point (refused until it is surveyed) makes a site with `place: 'point'` and `where` `jump-point` (id the jump id) whose first building is one of `data_centre` and `jump_point_stabiliser`; other ships `dock` there from the point. A data centre may stand there, since the stabiliser's 10 million compute units are made where it stands. A stabiliser at the site and milestone 29 done marks the point stable and logs the event that ends the prototype (`jump.ts` `settleJumps`, run by `advanceShips`). Nothing travels through it. The map labels it unsurveyed, unstable or stable and selects it.
- **A platform at a giant.** A ship in orbit of a body it cannot land on (`NO_SURFACE`: Venus and the four giants) founds a site with `place: 'surface'` that hangs in the air: ships `dock` to it from orbit, it counts as an orbit place for trips, and it extracts the atmosphere's materials (the scoop at Jupiter, Saturn, Uranus or Neptune, the skimmer at Venus).
- **Orders** (`orders.ts`): `fly` (to a body's orbit), `land` (on a body's surface; the vessel is at the site there if one exists), `dock` (from the orbit of a site's body into the site, one hour), `load` and `unload` (cargo by material, propellant by kind, or crew, four hours, the amount or all that fits), `wait`. `goTo(v, site)` adds the orders that reach a site. Orders run in sequence inside a step at their own times; a blocked order keeps its place and the vessel's `blocked` says why. Docking ignores the angle between a ship's orbit and a station's (**placeholder**).
- **Sites off Earth.** An economy `Site` has `place` (`surface`, `orbit` or `point`), `angle` (its orbit phase), `berths` (people it can house; `null` on Earth), `launches` and a `yard` queue beside its stock, groups and construction queue, and runs the same flows as Earth. `foundSite(game, v, buildingId)` turns a ship in free orbit or landed with no site into a site (`orbit-<body>` or the body's id): the ship's cargo must hold the building's cost, which is spent, and the building stands at once; the rest of the cargo and the propellant go into stock, the crew become the population, the ship's berths become `berths`, its solar power becomes `gridKw`, and the ship is consumed. One orbital site and one surface site a body. `installModule(game, v)` does the same for a ship docked at an existing site. Population there does not grow; people eat the site's food stock, so a station starves unless food is delivered or made. Buildings stand only where their `where` allows. **A milestone's building needs are met by a building standing at any site**, so an orbit-only building (a propellant depot, a life support plant) is satisfied by a station.
- **Make or import** (`supply.ts`, the Supply tab): `supplyRows(game, site)` lists what a site off Earth wants (inputs of its groups, builds and programmes, and its people's food) with what it makes, its stock and, for each other site with stock, `importCost`: the propellant a tonne costs by the best freighter design the player owns (a round trip with a full hold from `planTrip`), or by launch (the last launch's propellant for a full load) from a surface site with air. `startRun(game, v, { item, amount, from, to })` sets a vessel's orders to the cycle `load propellant, load cargo, go, unload, come back` and repeats it (`v.run`); it is refused from or to a launch site. `clearOrders` stops it.
- **Founding the first station by play** needs the first building to be one the milestone records have unlocked: after milestone 1 a station can start with a chemical plant, an alloy works and the other milestone 1 buildings, and after milestone 2 with a propellant depot. The player has no power in orbit before milestone 4, so a crewed ship (any crew or habitat part draws power) cannot be locked before the solar array is unlocked.
- **Fuel cell, sample and landing drive.** The `fuel_cell` component lets a crewed design be locked at milestone 3 (a power-deficit warning gives its hours). A `sample` order (`ships/sample.ts`: `SAMPLE_KG` 1, `SAMPLE_DAYS` 2, placeholders) takes the first deposit of an asteroid's region into the hold of a ship in orbit of or on it with a `sampling_arm` (`samples: true`) and room; unloaded at a site it is ordinary stock. A landing or an ascent uses the drive with the most thrust that the ship holds propellant for (`hopShip`, `Hop.fuel`), so a ship on ion thrusters that also carries one chemical engine and a tank can land on an asteroid that pulls 1 kN on it, burning the chemical propellant and leaving the xenon.
- **The scripted player** (`game/play.ts` `Player`, `game/playPath.ts` `PathPlayer`, `game/playJump.ts` `JumpPlayer`, `game/playOuter.ts` `OuterPlayer`) plays from the start state: it switches recipes, queues buildings, designs a booster and an orbiter, builds and launches them, founds the station with the first building a milestone needs, builds the orbit-only buildings from cargo, and (after milestone 4) launches a habitat module with six crew. `PathPlayer` carries on to milestone 17: heavy stacks (nine and three methalox engines, 68 t to orbit) carry propellant to the station depot (each fill takes only the component the station lacks, so lunar oxygen in stock saves launches), a lander puts four crew and a year of rations in the south polar region (6), one-way haulers bring the reactors with haleu (7), the ice mine, excavator and the kit for the later buildings (8), the oxygen plant and sinter printer are built from that stock (9, 10), the greenhouse (11), electrolysis and liquefaction plants (12); `cislunarSupply()` then sends a hydrolox tanker to fuel from lunar water and carry 20 t of lunar oxygen to the station, and records the tonnes of propellant a tonne costs from the Moon against `importCost` by launch from Earth; after 13 a nuclear electric tug (14 ion thrusters, six reactor ships, a methalox engine to land) leaves for Hertha, 15 is a methalox probe that surveys and samples Bennu and docks at the station, 16 a nuclear thermal hauler that lands the miner and processor on Bennu, 17 founds the miner and refinery on Hertha when the tug arrives. Its timeline is set by placeholders: programme lengths (60 days plus 30 a step, 300 to 700 days), the three build slots of a site, one yard group building one ship at a time, and the planner's windows (Bennu is 6 years from Earth in synodic period, the tug takes about 10 years of thrust at 3 N). `JumpPlayer` keeps every crewed site fed and the station running; `OuterPlayer` carries on to milestone 29, and `play.test.ts` runs it in four stages that share one game (1 to 17, 18 to 21, 22 to 24, 25 to 29, about 2.7 minutes in all) and asserts the dates, launches, sites and that no populated site was ever hungry (`player.hunger`). Rules the player follows after 17: food is not made on Earth, whose stocks run out by about 2044 as its population grows, so the first crewed station buys a reserve of wheat in 14 heavy launches that the station crew, the Moon shuttles (`moonFood`, every ~6 years), the maria lander and the jump point founder eat from; the station holds 300 kg of haleu and 3 t of AI accelerators for its reactor and data centre and the player tops them up; Earth makes only what the economy has spare, so `supplyRate` asks for 20 percent more than a material's current use and `billRate` spreads a bill over 45 days instead of 48 hours (a bill for a plant that makes grams an hour would queue thousands of plants on three build slots). Steel for the shipyard and the solar station comes from Hertha by `jump-barge`: a tug of 20 reactors and 29 ion thrusters launched with the Hertha tug after milestone 13 with 150 t of xenon and 3 t of carbon (Hertha has no carbon to refine steel with), 13 years each way for 52 t, because a spiral from low Earth orbit alone costs 7.8 km/s and Hertha to Earth needs 18.5. After 24 the steel for the scoop, the exotic matter facility and the stabiliser (240 t) comes in one run of `jump-hauler`, a fusion ship of two drives (a design holds at most 99 of a part, a drive makes 2 MW of waste heat and a radiator sheds 50 kW, so two drives is the most one design can cool), 60 cargo bays and 48 tanks; the scoop goes to Uranus on a one-drive carrier, and the stabiliser site is founded by `jump-founder` with six crew, a data centre and 26 t of wheat, then fed steel by the hauler, which is installed there for its power. Deuterium for all of it comes from 200 isotope separators on Earth (0.1 kg an hour each). `?test` in a dev build puts it on `window.space4xTest` for `tests/travel.spec.ts`. `?scenario=travel` seeds designs, a launch, a station, an outpost and a ship on a trip for the layout states. `?scenario=belt` seeds a survey probe at Mars, one at Bennu and a lander on the Moon with cargo (`&outpost` also founds an ice mine at the south pole), and `?surveyed=mars,eros` marks bodies surveyed, for the belt tests. `?scenario=jump` puts a survey probe at the jump point and one in Earth orbit with milestones 1 to 28 reached (`&outpost` also surveys the point and founds an outpost there with a data centre and steel), for the jump point tests in `tests/belt.spec.ts`.

## Adding a system

A system is a function `(game, dtSeconds) => void` that `game.advance` calls on every tick. Put a screen's simulation in `src/lib/screens/<id>/system.ts`:

```ts
import { registerSystem } from '#lib/game/index.ts';
import { projects } from './projects.svelte.ts';

registerSystem('research', (_game, dt) => {
  for (const p of projects) p.done = Math.min(1, p.done + p.rate * dt);
});
```

`screens/index.ts` loads every `screens/*/system.ts`, so nothing shared needs editing. Registering a name again replaces the earlier function. Systems run in the order they are registered; `orbits` and `contacts` run first; `economy` runs the economy and then the ships. Test a system with vitest by building a `new Game()` and calling `advance`.

## Adding a screen

Each screen owns exactly one folder, `src/lib/screens/<id>/`. Replace its placeholder `Screen.svelte`; put its components, drawing code, mock data and system in the same folder (or its mock data in `game/mock/<domain>.ts`). Do not edit another screen's folder or the shared files to make room for yours; if a shared primitive is missing something, extend the primitive.

A grid screen's root is `ScreenGrid`, which renders `<main class="screen" data-screen="<id>">` straight under `#stage`, where the layout check looks for it:

```svelte
<ScreenGrid id="economy" columns="320px minmax(0,1fr)">
  <Stack>
    <Panel title="Colonies"><Table head={['Colony', '>People']} {rows} /></Panel>
    <Panel title="Mars" grow body="col"><CanvasView scale={2} bg="stars" draw={drawPlanet} /></Panel>
  </Stack>
  <Stack>...</Stack>
</ScreenGrid>
```

Only the map stays mounted when another screen is shown; any other screen is mounted when it opens and dropped when it closes, so state that must survive a switch lives in a module-level `$state` in the screen's folder. A screen's URL parameters are applied once at load, not when the screen mounts: export an `applyXParams(params: URLSearchParams)` from the screen's state module and call it from `screens/params.ts`. After that the module state wins, so a button that sets that state and then opens the screen (`showColony(id)`, then `shell.setScreen('economy')`) is not overridden.

## Icons, tiles and formatting

The management screens are built from icon tiles and cards, not text tables. The look is `mockup/ui/`; what it needs is below, so read this instead of the mockup's code. Everything is exported from `#lib/ui/index.ts` (components, `fmt`, tooltip helpers) and `#lib/gfx/index.ts` (icon functions). `/dev/tiles` (gallery build) shows every primitive and the whole icon set; `tests/primitives.spec.ts` covers it.

### Icon functions (`src/lib/gfx/icons/`)

- `materialIcon(id)`, `buildingIcon(id)`, `componentIcon(id)` return a PNG data URL, rendered once and cached. Sizes: materials and components 16 by 16, buildings 24 by 20 (`ICON_SIZE`). Draw them with `image-rendering: pixelated` at whole multiples; `PixIcon` does it.
- `IconRef` is `{ kind: 'material' | 'building' | 'component', id }`; `iconUrl(ref)` and `iconSprite(ref)` (`{ url, width, height, pixels }`) take one.
- The pixels are the mockup's, checked id by id against it (`icons.test.ts`, fixture `mockup-hashes.json`). A material's shape follows its category, its colour and two-letter mark come from tables in `materials.ts`; a material in the data without a colour gets the mockup's generated hue.
- An id the tables do not know is never blank. A material the data holds is drawn by its category; an id not in the data is a grey orb; a building is a hangar and a component a box, tinted by its `kind`. `hasIconArt(ref)` is false for those, and `icons.test.ts` lists them (today: none; the three nuclear fuel materials list the colour the mockup generated for them, because a generated hue follows a material's index in its category). Draw a new id in the generator file, add its hash to `mockup-hashes.json` only if the mockup has it, and the list in the test shrinks.
- `materialLook(id)` gives `{ base, R, shape, code }` (the colour ramp, for bars coloured like the material). `CATEGORY_NAMES`, `CATEGORY_ORDER`, `CATEGORY_EXAMPLES` (one material per category), `BUILDING_KIND_NAMES`, `COMPONENT_KIND_NAMES`, `KIND_COLOURS` (the stripe colour of a building or component kind) and `KIND_EXAMPLES` are the vocabulary for filters and headings; `categoryName(c)`, `buildingKindName(k)`, `componentKindName(k)` give a human name for any value.
- The 11 by 11 glyphs live in `gfx/icons.ts` (`ICONS`, drawn by `Icon`); the mockup's new ones (`up`, `down`, `flat`, `lock`, `check`, `plus`, `minus`, `cross`, `hammer`, `box`, `power`, `clock`, `trash`, `flame`, `wrench`, `rocket`, `leaf`, `atom`, `arrowR`, `filter`) are in it. `Icon` takes `class="xs"` (11 px), `"sm"` (14), `"lg"` (33).

### Portraits (`src/lib/gfx/portraits/`)

Officer faces, ported from `mockup/ui/js/portrait.js` with the drawing code and the random-number order unchanged, so the same input gives the same pixels. Import from `#lib/gfx/portraits/index.ts` (also re-exported by `#lib/gfx/index.ts`). It draws without a browser canvas and renders each picture once to a PNG data URL through the icon encoder.

- `portraitBust(spec, style?, over?)` returns the 64 by 72 bust (`PORTRAIT_W`, `PORTRAIT_H`) as a `Sprite` (`{ url, width, height, pixels }`); `portraitHead(spec, style?, over?)` the 32 by 36 head crop of the same picture (`HEAD_W`, `HEAD_H`), for tiles. Both are cached by spec, style and overrides: the same arguments return the same object.
- `spec` is a `PortraitSpec`: `seed`, `age` (from the game clock; it greys the hair and lines the face), `rank` (0 to 5; from 2 a peaked cap is possible, ribbons grow), `branch` (`staff`, `ground` or `governor`, the uniform colour), `gender` (`m` or `f`) and optionally `rolledAt` (`{ age, rank }`). The mockup rolls its traits in one sequence whose length depends on age and rank (greying, the tired eyes after 55, the cap from rank 2), so a bare spec gives another face when the age or rank changes. With `rolledAt` the face (everything but hair colour, age lines, ribbons and whether the cap shows) is rolled at that age and rank and stays; only the hair colour and lines follow `age`, and a cap shows from rank 2 if it was rolled. Leave it out to get the mockup's picture for that exact age and rank; the pixel test does. An officer uses `rolledAt` with their age at the start of the game and a rank of 2 or more.
- `style` is `gritty` (default, `DEFAULT_PORTRAIT_STYLE`) or `clean`; `PORTRAIT_STYLES` lists both with names. The game uses the default; the switch is only on the showcase.
- `traitsOf(spec)` returns the rolled `Traits` (skin, eye colour, hair colour and style, jaw, eyes, brow, nose, mouth, lip, beard, gear, cap, earring, eye shadow); `over` replaces any of them (the showcase uses it to show one option at a time).
- The catalogue: `HAIRS` (21 styles; `hairGenders(id)` and `hairFor(gender)` say who can roll each: men only, women only or both), `BEARDS` (12, men only), `EYES`, `BROWS`, `MOUTHS`, `GEARS` (eyepatch, shades, headset, scar, implant), `SKIN`, `HAIR`, `GREY`, `EYE`, `BALDING` (bald, bald on top and receding: men only), and `ROLLS`, the per-gender tables `traitsOf` picks from.
- Checked against the mockup: `portraits.test.ts` hashes 480 busts and heads (120 seeds, both genders, both styles) and every catalogue option in both styles against the mockup script run in node (fixture `mockup-hashes.json`): identical.
- `Portrait` (`spec`, `view` `bust` or `head`, `scale`, `style`, `over`, `tip`) draws one as a pixelated image. `/dev/portraits` (gallery build) shows the whole catalogue with the Clean and Gritty switch.
- Officers (`screens/commanders/roster.svelte.ts`) carry `gender` and `seed`; `portraitSpec(officer, game.time)` builds the spec (a governor wears the governor uniform, everyone else staff blue). A screen that shows an officer uses it, never its own face.

### Formatting (`src/lib/ui/format.ts`, `fmt` from `#lib/ui/index.ts`)

Pure functions, tested in `format.test.ts`. Quantities come in SI base units as the game holds them (kilograms, kilowatts, newtons, seconds) and leave in the unit the screens show.

- `group(n)` and `count(n)`: whole number with thousands separators. `num(v)`: 0 decimals from 100, 1 from 10, 2 from 0.1, 3 below, `0` under 0.0005.
- `mass(kg)` gives tonnes (`2.5 t`, `0.005 t`), `power(kW)` megawatts, `thrust(N)` kilonewtons, `people(n)` millions (`8,200 M`), `pct(fraction)`, `amount(a, unit?)` by the material's unit (`kg` as tonnes, `cu`, `model`).
- `days(d)` (`13 d`, `1.1 y`, `never`) and `duration(seconds)` (`30 s`, `10 min`, `2 h`, then days).
- Gain and loss: `signed(value, text)`, `signedAmount`, `signedPower`, `signedPct` (a zero shows as `0`, no sign); `toneOf(change)` is `cool`, `hot` or `dim`; `trend(net, stock?)` is `up`, `down` or `flat` (flat when tiny against the stock) and `trendTone(trend)` its tone.
- Rates: `PERIODS` (`day`, `year`), `perHour(perSecond)`, `rate(perHour, period, unit?, signed?)` (`24 t/d`, `+8,760 t/yr`, `0`).

## The Economy screen

`screens/economy/Screen.svelte` is a site list and the planet on the left, and on the right one panel with icon tabs and the rate switch (`rates a day | year`, `ui.period`, day by default, read by every rate through `fmt.rate`). ## Scripts and the remote runner

`pnpm check` runs only the legs the change needs and `pnpm check:all` runs all six. `tools/ci/gate.mjs` reads the same change scope as CI (`tools/ci/scope.json`): it diffs against the merge-base with `origin/dev` (`--base <ref>` overrides; uncommitted and untracked files count), runs `check:types`, `lint`, `knip`, `format:check`, `test`, `test:layout` in that order for the legs that are true, prints which run and which are skipped, and stops at the first failure with its exit code. A docs-only change runs none. `node --test 'tools/ci/*.test.mjs'` tests the leg selection. `pnpm check`, `pnpm check:all`, `pnpm test` and `pnpm test:layout` go through `tools/remote/run.mjs`: on that server, or with `CI=true`, they run in place; anywhere else they send the committed `HEAD` to the server over ssh and run it there and never fall back to the local machine; commit first. They forward `SPACE4X_*`, `VITEST_*`, `SHOTS`, `SIZE` and `PORT`; `SPACE4X_FETCH=<dir>` copies a directory back afterwards.

The Playwright web server picks a free port, or uses `PORT` when it is set, so several checkouts can run at once.

## The layout test is the gate for UI work

`tests/layout.spec.ts` loads every query state at 1440x900 (`SIZE=w,h` overrides it) with `?check` and fails with the messages of `src/lib/ui/layoutCheck.ts`: gaps, overlaps, panels off an edge, clipped or cut-off content, cells past an edge, squashed frames, canvases not filling their frames, scroll and empty-space imbalance, overlapping map labels, labels under windows, a wrapped top bar and a scrolling page. A screen whose `Screen.svelte` still renders `<Placeholder` is `fixme`; replacing the placeholder turns its states on, and they must pass before the work is done. `tests/interaction.spec.ts` covers the clock, steps, screen switching and every window operation; `tests/primitives.spec.ts` covers the shared primitives on `/dev/primitives` and the tile kit and icon set on `/dev/tiles`.

For a change to layout or behaviour, also look at the result: `SHOTS=<dir> pnpm test:layout`, then open the PNGs next to the mockup in the same state.

## Conventions

- No comments anywhere: not in code, config or tests. Use clearer names, smaller functions, or a test.
- Never render an internal identifier to the player; show a human label.
- Mock content stays visibly mock and in the gallery only: a mock scene or screen carries a "mock scene" tag (`.tag`) on itself. The top bar starts with the game's icon and name, and has no room for a tag beside them at 1440 px.
- Management screens are icon tiles with names, a card for the selected tile, tooltips with a description and the numbers, and one unit per quantity (tonnes, MW, kN, people in millions, rates a day or a year), as in `mockup/ui/` and the section "Icons, tiles and formatting". Tables only where a long list of like rows cannot be tiles. Icons, not text, for screen buttons and status values; no gaps; nothing laid over the map except the windows; one Selection window for whatever is selected; screen buttons switch whole screens, never popups.
- Commit messages say why and how the change was verified.

## Branches, promotion and the dev build

`dev` is the default branch: features and fixes land on it through pull requests (a feature of ten commits or more) or direct commits (everything smaller), as the global rules say, and CI (`.github/workflows/ci.yml`) runs on pushes to `dev` and `main` and on every pull request. `main` moves only by `pnpm promote`, after a playtest of the dev build at https://space4x.callmedaddy.dedyn.io/. Branch from `dev`, open pull requests against `dev`, and never push `main`.

- `pnpm promote --list` shows the commits and merged pull requests on `origin/dev` that `origin/main` lacks.
- `pnpm promote` merges `origin/dev` onto `origin/main` in the worktree `.claude/worktrees/promote` as branch `promote/main`, pushes that branch, and waits for `.github/workflows/promote.yml` on that commit. It reuses an unchanged candidate (same `main` and `dev` parents). Green, it installs dependencies in the worktree and prints the playtest steps: the dev build, and `cd .claude/worktrees/promote && pnpm dev` for the candidate itself. Red, `main` is untouched and the worktree stays for a look.
- `pnpm promote --push` pushes the green candidate to `main` and removes the worktree.
- `promote.yml` runs on `promote/**` pushes and by `workflow_dispatch`: `pnpm check:all` and `pnpm build`. It is listed under `"full"` in `tools/ci/scope.json` because it runs every leg on purpose.

### The dev build

`install.sh` installs the user units of `deploy/` for the checkout it is run from, which must be on `dev` (`HOST` overrides the machine's Tailscale address, `PORT` overrides `8800`). It does not touch `deploy/runner/`, which `deploy/runner/setup.sh` owns.

- `space4x-serve.service` serves `build/` with `tools/serve.mjs` (a static server with a single-page fallback) on the machine's Tailscale address, port 8800; Caddy publishes it as https://space4x.callmedaddy.dedyn.io/. Before it starts, `deploy/build --if-stale` runs `pnpm install --frozen-lockfile` and `pnpm build` unless `build/.built-head` already names `HEAD`.
- `space4x-update.path` fires `space4x-update.service` when `.git/refs/heads/dev` or `.git/refs/remotes/origin/dev` changes. `deploy/update` does nothing unless the checkout is on `dev`; with a clean tree it fast-forwards `dev` from `origin/dev`, and when `HEAD` is not what `build/` was built from it rebuilds and restarts the server (or re-runs `install.sh` first when `deploy/` or `install.sh` changed).
- Nothing in the repo fetches. `git-autofetch.timer` fetches every repo under `~/Documents/Projects` every two minutes, which moves `origin/dev` and so triggers the path unit.
- Keep the main checkout `~/Documents/Projects/Space4x` on `dev` with a clean tree: it is what the build serves. Check it with `systemctl --user status space4x-serve.service space4x-update.path` and `journalctl --user -u space4x-update.service -n 50`.
