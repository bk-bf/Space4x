# AGENTS.md: Space4x

How to work on this code as it is now. Plans, decisions and findings go in issues, pull requests and commit messages, not here.

## The code is the ground truth

If something is unclear, find out from the code: grep for it, read it, run it. Do not infer it from a document, a name, or from what a game like this usually does. State what you checked.

## Stack

SvelteKit 3 with Svelte 5 runes and strict TypeScript, built by `@sveltejs/adapter-static` as a single-page app (`ssr = false`, fallback `index.html`), which the Tauri 2 shell in `src-tauri/` embeds (see The desktop build). pnpm only; never npm, npx or yarn (`pnpm dlx` for one-offs). Commit `pnpm-lock.yaml`.

Imports inside `src/` go through the `#lib/*` subpath import in `package.json` and name the file with its extension: `import { game } from '#lib/game/index.ts'`. SvelteKit 3 has no `$lib`.

Use runes (`$state`, `$derived`, `$effect`, `$props`); not the legacy `$:` syntax or stores.

## Game and gallery

Nothing mock is shown in the game build. `VITE_SPACE4X_GALLERY=1` selects the gallery build, which shows everything; `gallery` from `#lib/shell/mode.ts` is the only reader of it. In the game, `mockWorld()` has no sites (so no site scene, marker or fly-to button), `SCREENS` lists only screens with `mock: false` (so the top bar, F keys, `?screen=` and `isScreenId` ignore the rest).

Every entry in `screens/list.ts` carries `mock: boolean`. To make a screen real, change its `mock` to `false`; nothing else. New mock content (a scene, a list, a button) is wrapped in `gallery` so the game build never renders it. `./launch.sh --gallery` builds the gallery and opens it in the desktop shell (see The desktop build).

Tests: Playwright has two projects, each with its own dev server. `gallery` runs everything but `tests/game.spec.ts`; `game` runs `tests/layout.spec.ts` (states marked `mock` in `tests/states.ts` are skipped) and `tests/game.spec.ts`. A layout state that needs a mock screen or site goes in `tests/states.ts` as before; a site-only query also goes in `SITE_QUERIES`. Vitest runs with the gallery on (`vitest.config.ts`); `src/lib/shell/mode.test.ts` covers the game mode.

## Game state

`game` (from `#lib/game/index.ts`) is the one `Game`. Its fields are runes, so components read them directly and update when they change.

- `game.time` (ms, UTC), `game.elapsed` (game seconds since the start), `game.running`, `game.step` (seconds)
- `game.world`: `bodies` (the 8 planets and 7 moons of `mock/bodies.ts`, then `moonBodies`, `asteroidBodies` and `cometBodies` from the data: about 585 bodies), `fleets`, `contacts` (each names its `system`), `systems` (stars, belt, jump points), `system` (the one the map shows); `game.events`; `game.status` (the top bar chips, read-only: see below)
- a body with `colony: true` is a colony, and the economy holds one site for it whose `worldBody` is that body's id (`siteById(bodyId)` finds it), so add a colony as a colonised body and an economy site together. A body with `parent` is a moon and `bodyPosition(body, bodies)` places it around that body; a dwarf planet can be a parent
- `game.body(id)`, `game.fleet(id)`, `game.contact(id)`, `game.starSystem(id)`, `game.jump(id)`, `game.systemOf(selection)`
- `game.world.fleets` and their `orders` are mock data for the gallery and test fixtures only; nothing moves them. Real ships are `ships.vessels` (see Ships below)
- `game.selection`: `{ kind: 'fleet' | 'body' | 'contact' | 'site' | 'ship' | 'base', id }` (`ship` is a vessel id, `base` an economy site id); set it with `select(kind, id)` from `#lib/ui/index.ts`, which also shows the Selection window
- `game.advance(seconds)`, `game.setStep(seconds)` (single-steps when paused), `game.run()`, `game.pause()`, `game.toggleRunning()`, `game.log(category, text, warn, { at, subject })` (an event files by its time; a `subject` makes it select that object when clicked)

While running, the loop advances `game.step` of game time per real second, ten ticks a second.

### Ship classes

There are no premade classes. `game/classes.svelte.ts` holds the one registry (`classes`, starts empty) of the `ShipDesign`s the player makes: `shipClasses()`, `shipClass(id)` (the drawable top-down spec, built once per design object), `classStats(id)`, `className(id)`. A ship keeps only its `classId`. The Ship classes screen edits the registry; Economy, the map and Intelligence read it and must cope with it being empty. The mock fleets still name classes that no longer exist, so `className` gives them `Unknown class` and the map draws them as markers. A screen that keeps a class in use (a yard tooled for it) registers `registerClassUse` so the designer will not delete it. `game/design.ts` is only the drawing geometry (`layout()`, `lengthOf()`); `gfx/ships/specs.ts` `SPECS` are art for the mock scenes, not classes.

### Ship design

`src/lib/game/shipdesign/` (import from `#lib/game/shipdesign/index.ts`) is pure TypeScript with no Svelte. A `ShipDesign` is `{ id, name, role, yard, parts: [{ component, count }], load, locked }`: `role` is one of `ROLES` (launcher, transfer, lander, capsule, freighter, probe), `yard` is `rocket_factory` (on Earth, so the ship must lift off from it) or `orbital_shipyard`, `load` is kilograms of each `PropellantKind`. Edit it only with the functions in `edit.ts` (`setCount`, `addPart`, `removePart`, `setLoad`, `rename`, `setRole`, `setYard`, `copyOf`, `lock`, `canLock`): each returns a new object, a locked design comes back unchanged, and tanks that were full stay full as parts change. A class that is locked can only be copied.

**Component figures** are the `design` record of each entry in `components.json`: `mass` kg (an engine takes it from `performance.mass`), `crew` needed aboard (a reactor or drive needs an operator unless some component `automates`, as avionics does; a capsule's own crew stays), `housing` berths, `stores` kg of consumables, `supports` crew a life support unit sustains, `power` kW drawn, `generates` kW made at 1 AU, `storage` kWh (a battery, or the `fuel_cell`: hydrogen and oxygen reactants with the stack, 500 kWh, open from the start, estimated, which lets a capsule fly before any solar array or battery exists), `heat` kW of waste heat (defaults to `power`), `radiates` kW, `volume` m3 of tank, `propellants` (a tank holds them, an engine burns its one), `cargo` kg, `landing` and `reentry` kg a set of legs or a heat shield handles, `insulates`, `boost` (a booster: `{ propellant, load }`, the propellant it carries and burns before the ship's own drive; its `performance` gives Isp, vacuum and sea-level thrust and mass), plus `basis` (how the figure comes about), `source` (a URL where it is real) and `estimated`. Propellant kinds in `propellants.ts` give the bulk density in a tank, the materials of the mix and whether it is cryogenic; tank room is the volume shared between the kinds that tank accepts.

**`designStats(design, unlocked?)`** (`unlocked` is a predicate over research tags, everything open by default; component figures come through `component(id)`, which applies the ship boost lines: `setComponentBoosts` in `boosts.ts`, set by `classes.svelte.ts` from `economy.done`, multiplies a booster's thrust and propellant, the solar array's output and the battery pack's storage, and `statsFor` keys its cache on `boostKey()`) returns `lines` (count, mass, material cost per component, boosters included), `dryMass` (boosters left out: the ship in orbit no longer has them), `boosters` (count, mass, propellant kind and load, Isp and thrust, or nothing), `climb` (`climbWith(stats, payload)` at a full bay: see Boosters below), `propellant` and `capacity` by kind, `payloadCapacity`, `loaded` (full tanks and bay) and `empty` (no payload) conditions each with `mass`, `deltaV` (through `shipDeltaV`), `acceleration` and `thrustToWeight` and `liftoff` on `earth`, `moon` and `mars` (sea-level thrust on Earth, `MIN_LIFTOFF_TWR`), `drives` and `main` (the drive with the most delta-v; engines of one propellant add up with a thrust-weighted Isp), `crew`, `berths`, `stores`, `endurance` days (5 kg a person a day without a life support unit, 1 with), `power` (made, used, engines, balance, storage), `heat` (produced, radiated with 0.5 kW a tonne passive, balance), `builtAt` (yards that can build every part), `cost` and `propellantCost` in materials, and `issues` with `errors` and `warnings`. A class can be locked only with no errors. Errors: no parts, a locked component, no engine, no tank for the engine's propellant, no propellant loaded, crew without berths or stores, power deficit (stored energy, a battery or a fuel cell, turns it into a warning that gives the hours it lasts), heat deficit, a yard that cannot build the parts, a lander without legs or overloading them, a return capsule without a heat shield or overloading it, a freighter without a cargo bay. Warnings, for a design built at the shipyard on Earth: lift-off thrust to weight under `MIN_LIFTOFF_TWR` and delta-v to orbit short of `surfaceToOrbit(earth)`, both from `climb`; for any design: load that does not fit, a throttled electric drive, no battery for an eclipse, a reactor beside the crew without a shield, cryogenic propellant without insulation on anything but a launcher, a lander too weak to hover on the Moon.

**Boosters** (`climb.ts`, #66). A `booster` is a ship part, built only at the shipyard on Earth, not a drive (`isEngine` leaves it out, `isBooster` finds it): one thirty-third of Super Heavy Block 1, so 33 of them are one Super Heavy (275 t empty, 3,400 t of methalox, 73.5 MN at lift-off, Isp 347 s in vacuum; `estimated`). `climbFrom(body, boosters, ship)` is the climb from a surface to low orbit: lift-off thrust is the boosters' sea-level thrust when there are any, else the ship's drive's, checked against `MIN_LIFTOFF_TWR`; the boosters burn all their propellant with the whole ship riding and are dropped, then the ship's drive with the most thrust that holds propellant (`climbDrive`) makes up the rest of `surfaceToOrbit`, with the other propellants and the payload as dead mass. A booster's mass ratio (111 t full, 8.3 t empty) is below the 15.8 that 9.4 km/s needs, so boosters alone never reach orbit. `Climb` gives `boosters`, `boosterMass`, `boosterLoad`, `liftoffMass`, `liftoffThrust`, `twr`, `boosterDv`, `shipDv`, `deltaV` (their sum), `need`, `boosterBurned`, `shipBurned`, `leftover` (the ship's propellant left in orbit) and `reaches`; `climbReasons` words a shortfall. `builtMass(stats)` (dry mass and boosters) is what the shipyard builds and what `shipyardsFor` and the points read. Whether a dropped booster can be recovered and launching from another body are left open on #66; the booster has no icon art or top-down art yet.

**For flight:** `flightShip(design, { propellant?, payload? })` returns what `planTrip` takes (`{ dryMass, payload, propellant, engine, powerAvailable }`) or `undefined` with no engine: `dryMass` includes the other propellants carried, `engine` is the main drive added up (`thrust`, `thrustSeaLevel` and `power` are totals, `count` is left out), `propellant` and `payload` default to the full propellant load and an empty bay and are clamped to what the design holds. `designSpec(design)` (`art.ts`) maps the components to the top-down generator's parts: engines to the stern (`big` for four or more or a nuclear or fusion drive), tanks, reactors, habitats, trusses and cargo bays to sections (a count of n gives `1 + floor(log2 n)` sections up to a cap), solar arrays, radiators, thrusters, legs and antennas to attachment slots, and a capsule, adapter or heat shield to the bow.

**The screen** (`screens/classes/`) edits the registry live with no save step, in the mockup's three columns. Left, `Palette`: every component as a `cmp` tile grouped by kind (`KIND_NAMES`), with its name and a key figure (Isp for an engine, mass otherwise), `×n` when the open class holds it, a tooltip of its figures (`factList`), and a locked one dimmed, disabled and marked `locked`, its tooltip naming the prerequisites it waits for; clicking a tile adds one, and with no class open starts one with it. Middle, the drawing (the real top-down generator through `drawDesign`, with its length and beam) above the `Class` panel: New, Copy, Lock and Delete in its title bar, the class list (`#classList`, one button per saved class), the name (`#clsName`), role and built-at selects, and `Strip`, one tile per component with minus, a count input and plus. Right, `Stats`: the eight dense `Stat` tiles of the mockup (mass, delta-v, thrust to weight, thrust, crew, power, propellant, heat), the propellant load by kind with Fill and the payload shown (`Load`; the payload defaults to the bay and is lowered, never raised, since `flightShip` clamps it), `Flags` (every issue of `designStats` as an `error`, `warning` or `ok` flag with `data-issue`), the build cost as material icons, then, for a design built on Earth, the `Climb` section (`#climb`: delta-v against what orbit needs, the boosters' count and delta-v, the own drive's delta-v, lift-off thrust to weight and mass, payload to orbit `#climbCeiling` from `designCeiling`, and the verdict `#climbVerdict`) on the payload set under Load, and a second group of tiles for the figures the first eight leave out (delta-v empty, bay capacity, thrust to weight on Earth, the Moon and Mars, acceleration, life support days, where it can be built). Every figure is built in `figures.ts` from `designStats`, and each tile sits in a `data-stat` cell for the tests. A locked class disables every edit and can only be copied. `?screen=classes&new=stage` and `&new=crewed` open a ready design, and `&reached=<n>` marks projects 1 to n researched, for tests.

### Drawing ships

Every ship outside the System map is drawn top-down from its class design by `gfx/topdown/`, the port of `mockup/scenes/ships.js`. `gfx/ships/specs.ts` holds the shared vocabulary: the part keys (`CORE_KEYS`, `STERN_KEYS`, `BOW_KEYS`, `ATTACHMENT_KEYS`), their names (`PNAME`) the shipped `SPECS` (art for the mock scenes) and `designSpec()` in `game/shipdesign/art.ts`, which draws a class from its components. A design is laid stern to bow in units of `METRES_PER_UNIT` (5 m); `design.ts` `layout()` and `lengthOf()` read the same geometry, so a stat length is the drawn length.

Each part is built into a heightmap, material, component and emissive map once per class object and detail level (`LODS`, 0.375 to 12 px per 5 m) and cached on the class object, so an edited class (a new object) gets new sprites and an unchanged one is never rebuilt. A scale between two levels draws the next level up, scaled down. Each part and each hardpoint is its own component with a `kind` (system), a `name`, its `part` index in `layout()` order and its `slot`.

The API, from `#lib/gfx/index.ts` or `#lib/gfx/topdown/index.ts`, takes any `Pixels` (`w`, `h`, `d`, `px`; an `FB` is one) and screen positions, so a caller draws many ships from its own list of positions:

- `drawShip(fb, cls, { x, y, angle, pxPerMetre, sun?, frame?, livery?, thrust?, damage?, aim?, swap?, systems?, highlight?, dead?, cut?, build?, ghost?, clipX?, charging? })` draws true scale at the detail level for `pxPerMetre`, with drive plumes, turrets turned by `aim` (radians relative to the hull, one per `shipMounts` entry) and lighting from `sun` (screen angle towards the light; the mockup's default when left out). Returns `{ lod, scale, culled }`.
- `drawShipIcon(fb, cls, x, y, angle, sizePx, view?)` draws a fixed-size sprite, whatever the class length.
- `fitShip(cls, w, h, pad?, plumeRoom?)` gives the centre and `pxPerMetre` that fit a class into a box.
- `shipLengthMetres(cls)`, `shipBeamMetres(cls)`, `shipMounts(cls)` (metres from the ship centre, x towards the bow), `shipComponents(cls)`, `pickShip(cls, view, sx, sy)`, `nearestHull(cls, x, y)`, `detailLevel(pxPerMetre)`, `liveryOf(cls)`.
- `new ShipDamage()` holds hits in metres from the centre (`hit(x, y, radius, severity)`); pass it as `damage` and it is mapped onto each detail level once.
- `silhouette(fb, cls, view)` is the red treatment for an unidentified class.
- `drawStation(fb, 'core' | 'ring', view)`, `drawProp(fb, kind, view)` and `drawCraft(fb, 'fighter' | 'shuttle', view)` draw the mockup's stations, props and small craft.

`frame` is the animation counter for blinking lights, plumes and charging guns; screens pass three per frame-bus tick, as the mockup ran at 30 frames a second. Drawing cost grows with the pixels a ship covers, about 90 ns each: draw small ships with `drawShipIcon` rather than at a true scale that covers the screen many times over.

### Drawing small bodies

Asteroids and comet nuclei are small bodies (dwarf planets are not: see Drawing planets and moons). `smallBodyOf(body)` (`game/smallBodies.ts`) says which `Body` is small: an asteroid record that is not `dwarf`, or a body whose `facts.kind` is `Comet`; the Moon and Mercury are `rock` and keep their sphere, so never branch on the planet type. `gfx/bodies/small/` (import from `#lib/gfx/bodies/small/index.ts`) turns one into a `SmallBody`: `smallBody(info)` (`id`, `name`, `type`, `diameter` in km) picks a shape family from the name (`catalogue.ts` `NAMED`: Bennu, Ryugu and Didymos spinning tops, Itokawa and Arrokoth contact binaries, Eros and Ida peanuts, Apophis and Gaspra elongated, Kleopatra a dog bone, Mathilde, Lutetia and Psyche lumpy, Vesta, Pallas and Hygiea nearly round) and otherwise from diameter and a hash of the id; a type it does not know is stony. The macro shape is a `ShapeSpec` (`shape.ts`: lobes joined by a smooth maximum, low-frequency lumps, an equatorial ridge, and basins such as Vesta's, with a central peak, through `basinRelief`), normalised to a mean radius of 1. The surface is the broken-rock look of the approved bodies mockup ("Irregular shapes": faceted rock, shard, rubble pile, comet nucleus): `smallLook(body)` (`draw.ts`) builds a `craterLook` with `macro` set to the shape, `lumpy` from the family's entry in `ROCK` (`catalogue.ts`: displacement, lumps, crater dents, ridges and cut facet planes; rubble lumps for a body with many boulders, a waist for a one-lobe nucleus), the mockup's crater layers scaled by the spec's crater density and depth, and a palette by type (carbonaceous coal-dark, stony tan or grey-brown by seed, metallic cool grey, comet black with pale ice patches). It is drawn by the rock renderer below, like an irregular moon.

`drawSmallBody(fb, body, cx, cy, radius, turn, sun?)` is the one call; the radius is the mean radius in pixels, `turn` the rotation in radians on top of the body's own `phase` (`turnAt` below; the site list sprite passes 0, `/dev/bodies` turns with the frame counter), `sun` the screen angle towards the Sun as for `drawSphere`, and it returns the drawn outline as a `Box` (or nothing when off the frame), which the map uses to put the name beside the outline. `smallReach(body)` is the largest extent as a multiple of the radius (exact once the mesh is baked). A comet given a `CometTail` (`tail.ts`: `{ au, motion }`, its distance from the Sun and the screen angle it moves towards; only the map passes one, and `/dev/bodies` passes 1 AU) draws, behind the nucleus, light added to the sky rather than painted over it: a faint green-cyan coma brightest at the nucleus, a narrow blue ion tail straight away from `sun` with faint streamers of hashed noise along it, and a broad cream dust tail that bends behind `motion` (the map gives the prograde tangent of the comet's circular orbit). The light is quantised to six levels with interleaved gradient noise in place of the 4 by 4 dither, and nothing is random per frame, so a paused game draws the same tail. Its length is nine nucleus radii up to 230 px, times an activity by distance (`activityAt`: 1 inside 1 AU, 0.55 at 3, 0.18 at 5, none from 5.5 AU), so only comets on circles inside about 5 AU (Encke, Tempel 1, Wild) show one and Halley and Hale-Bopp are bare nuclei. It is drawn only between 5 and 40 px of radius: below, the comet is barely more than a mark; above, the nucleus fills the view. `tailReach` is how far it extends, which the map adds to the visibility test, so a comet whose tail is off the frame costs nothing and one whose nucleus is just off it still shows its tail. Each row is filled only across the hull where the tails can reach the light floor, about 72,000 pixels for 14,500 lit at 40 px. Baking is lazy: the first draw asks for the look and draws a disc in its tint until the mesh is baked, then the mesh in the tint until the surface is. Baked looks are held in least-recently-drawn order within 48 MB (`release`: the channel cube, mesh and normals of each look); a look over the budget is dropped and baked again if its body comes back into view (`heldLooks`, `heldBytes`, `smallReady`). On the map a small body is a one-pixel mark below 2.5 px of radius and costs nothing but its position. `/dev/bodies` (gallery build) shows every family, each named, at four sizes, and `small.test.ts` checks determinism, every named and generic shape at sizes 3 to 264, that a small turn moves the picture a fraction of what thirty of them do and a full turn comes back, the reach, the outline box and the memory budget. `?scenario=belt&asteroid=bennu` founds a miner site on an asteroid for the layout states.

**The rock renderer** (`gfx/bodies/rock/`) draws every irregular body: asteroids, comets, and every look with a `shapeFn` (Phobos, Deimos, Hyperion, Haumea and the family moons with a shape). It only finds which point of the surface each pixel sees; the colour and light of that point are the planets' own, from `shadeSpan` in `gfx/bodies/surface.ts`: a renderer fills one row of a `Span` (direction, geometric light, normal depth and x of each covered pixel) and `shadeSpan` colours it in one loop (the look's channel cube sampled at the direction, its `shade`, the bump from the baked gradients, Saturn's ring shadow, the dithered light levels, the dark side, city lights, sea glint and the atmosphere rim). `drawSphere` shades its rows the same way, so a rock and a planet of the same look are lit alike; a call per pixel instead cost the planets 15 to 26 percent. A look's `surface` is its radius as a function of direction: `macro` (an ellipsoid of `shape` when not given) times one plus the lumpy displacement. Its bake (`define.ts` `bakeSteps`) samples the surface at the 40,962 vertices of a level 6 icosphere (`mesh.ts`: levels 0 to 6 share a vertex prefix, so one array of positions serves every level), then bakes the channel cube like any look. A draw (`raster.ts` `drawRock`) picks the mesh level by size (`levelFor`: triangle edges of about 6 px, level 1 at the smallest, level 6 from about 175 px), transforms the vertices, lights each vertex from its normal, rasterises the front faces into a depth buffer at screen resolution, and shades each covered pixel once from the interpolated position and light. Cost per covered pixel is that of a planet plus the rasterising (on the slowest development machine about 55 ms for Earth filling the view, 65 ms for Apophis at its closest). A plain ellipsoid without lumps (none today) would still go through the sphere shader.

### Drawing planets and moons

Every planet, moon and dwarf planet is drawn by `drawSphere(fb, look, state, cx, cy, R)` (`gfx/bodies/sphere.ts`), where `look` is a `Look` and `state` is `{ rot, tilt?, pitch?, lights?, sun? }` (`orientation` in `light.ts` builds `rotY(rot) rotX(pitch) rotZ(-tilt)`; +y points down the screen; `sun` is the screen angle from the body towards the Sun, and `lightOf` turns `LIGHT` about the view axis to point there, keeping its height towards the viewer; without it the light is `LIGHT`, from the top left). The map passes `sun` for every body it draws; the Selection picture, the Economy panel and the thumbnails keep `LIGHT`. Any `Pixels` (`w`, `h`, `d`) will do, so sprites use it too. A look with a `surface` (a `shapeFn`) is handed to the rock renderer above and `drawSphere` returns its outline `Box`; every other look is drawn here: it writes opaque pixels, lights each pixel in seven levels (the four of `SHADES` and one between each pair), dithered by the 4 by 4 pattern of `dith`, so a sunlit side is dithered over its whole face rather than one flat level, and adds the atmosphere rim and halo, Saturn's rings, Earth's city lights (`lights`) and, for a look with `bump`, crater lighting from baked height gradients. `sphereReach(look, R)` is the extent in pixels.

A `Look` (`gfx/bodies/looks/types.ts`, made by `defineLook` or `craterLook`) is a list of channel functions of a unit direction baked once into a cube map (`gfx/bodies/cube.ts`: six faces of `face` texels, bilinear sampling, allocated on first bake) and a `shade(x, y, z, R, dv, G, O)` that turns the sampled channels `G` into a colour in `O` (`O[ADD]` brightens with relief, `O[LAND]` and `O[SEA]` mark land for city lights and sea for sun glint). `craterLook` builds the airless bodies from crater layers, features (named craters with rays), ring basins, a damp mask, extra height and three mask channels; its channel 0 is relief, 1 brightness of fresh craters, 2 a colour noise, 3 to 5 the masks `m1` to `m3` that each look's `post` colours; with `lumpy` it also gives a `shapeFn` (lumps, crater dents, facet planes, a waist) and with `macro` a radius of direction to displace instead of the `shape` ellipsoid. The planets use 256 texels a face, and `looks.test.ts` holds 24 hashes of their pixels; every other look uses 192, 128, 96 or 64.

Baking is lazy. `drawSphere` on a look that is not baked calls `want(look)` (`looks/bake.ts`) and draws a shaded disc in `look.tint`; `bakeStep` bakes in idle callbacks (`requestIdleCallback`, slices of at least 8 ms) and `onBaked` listeners fire when one finishes; `forget(look)` takes a look off the queue (the small bodies use it when they release one). `MapView` requests a render on each finish and asks for the planets, Mercury and the Moon when idle; the map repaints only if the finished look is one it draws on screen. `ui/bakes.svelte.ts` is the reactive counter that `planetSprite` reads so the site list redraws. `bakeNow(look)` bakes synchronously (tests), `bakeWanted()` bakes everything requested so far (the map bench calls `draw(0)`, then `bakeWanted()`, so the timings leave the bake out). A bake takes about 0.2 to 1.3 s a look (the crater looks at 192 texels are the slowest; a small body's look, with its mesh and paint cube, about 0.6 to 0.8 s).

Which look a body draws with is `lookIdOf(body)` in `game/looks.ts`: the body's id if it is one of `NAMED_LOOKS` (the 35 looks of `looks/index.ts`: Mercury, Venus, Earth, Moon (`luna`), Mars, Phobos, Deimos, Ceres, Jupiter, Io, Europa, Ganymede, Callisto, Saturn, Mimas, Enceladus, Tethys, Dione, Rhea, Titan, Hyperion, Iapetus, Uranus, Miranda, Ariel, Umbriel, Titania, Oberon, Neptune, Triton, Pluto, Charon, Eris, Haumea, Makemake); otherwise, for a moon record, a family and a seed (`moonFamily`): `captured` when the record is `irregular`, `rock` when it is carbonaceous, `rock` for an icy moon of Jupiter, Uranus or Neptune under 500 km (the records hold no albedo, and the real albedos of those small inner moons are near 0.1), `ice` for every other icy moon, with the JPL satellite `code` as the seed; for a dwarf planet record without a look of its own, `ice:<hash of id>:round` (a family look with no `shape`); otherwise by `Body.type` (`terran` to Earth, `gas` to Jupiter, `ice` to Uranus, `ice2` to Neptune, `rock` to `rock:1`). A family look id is `kind:seed` (`familyId`); `familyLook(kind, seed, round?)` (`looks/families.ts`) draws its tint, albedo, crater density, elongation, grooves, dark hemisphere and bright spots from the seed's random sequence, so a seed is the same body every time. `lookOf(body)` returns the `Look`; `smallBodyOf` returns nothing for a dwarf planet, so Ceres (the mockup's grey cratered ball with the Occator salt spots, chosen over a small-body Ceres because it keeps its crater relief at map sizes), Pluto, Eris, Haumea and Makemake draw as spheres (Haumea, being lumpy, through the rock renderer). `Look.facing` (degrees) is the longitude that faces the viewer in a static picture: `staticRot(look, fallback)` uses it for the map and the site thumbnails, and a look without it (the planets) keeps the old orbit-derived rotation; `Look.tilt` and `pitch` are set for the named moons and dwarf planets (Enceladus, Triton and Charon are turned to show their poles), and `sphereState(body, look, rot, lights)` falls back to `body.tilt`.

**Rotation.** Every body turns about its own axis with game time and only with game time, so a paused game draws the same picture and the map's frame cache serves it: `turnAt(body, game.elapsed)` (`game/looks.ts`) is minus one turn per `Body.rotation` hours (the sidereal period; negative for a retrograde body, which then turns the other way), added to the body's starting angle (`staticRot` for a sphere, `phase` for a small body). `Body.rotation` is set for the 15 bodies of `mock/bodies.ts` from the NASA planetary fact sheets (Venus and Uranus negative), for asteroids and comets from the record's `rotation`, for a regular moon as its orbital period (tidally locked), and for an irregular moon from the record. The map, the Selection picture and the Economy site panel use it; the site list thumbnails stay still. At the game's faster steps a body turns a large part of a turn between two ticks, as it would.

Callers: `drawMap.ts` (a `MapBody` holds `look` and `state`, and `box`, the outline last drawn, for the label; a body below the marker size is a mark and costs nothing), `selectionPicture.ts`, the Economy site panel (`planetView.ts`, `PlanetPanel.svelte`) and the site list thumbnail (`planetSprite.ts`). `/dev/planets` (gallery build) shows every named look grouped by planet system at four sizes, and the three families with eight seeds each; `tests/primitives.spec.ts` loads it, and `looks.test.ts` renders every named look at five sizes, bakes eight seeds of each family, checks seeded determinism and that every moon and dwarf planet resolves.

### Game data

The economy runs on JSON in `src/lib/game/data/`, so that a Rust simulation can read the same files later. `#lib/game/data/index.ts` loads them and exports the records (`materials`, `recipes`, `buildings`, `shipComponents`, `projects`, `startScientists`), lookups by id (`project(n)`, `projectById(id)`, (`material(id)`, `building(id)`, ...), and the derived graphs: `recipesProducing`, `recipesConsuming`, `recipesAt`, `materialSites` (where a material is extracted and where it can be made), `unlockedAt`, the unlock rule (`tagOpen`, `requiresDone`, `missingPrerequisites`, `dependentsOf`, `tagsOf`, `depthOf`, `boostOf`, see Research below), the `subjects`, `projectName`, and `reach`, which computes what exists from extraction alone, from the records tagged `upTo` a number or from a set of `tags`, on the thin path or the whole set, or on one site.

| Folder or file                     | Holds                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `materials/<category>.json`        | one small record per material; a category that outgrows about 400 lines gets `<category>-<part>.json`   |
| `recipes/<group>.json`             | a building turns `inputs` into `outputs`, each a map of material id to amount                           |
| `buildings/<kind>.json`            | where it stands, what it costs, who works it; extractors name the materials they work through `sources` |
| `components.json`, `research.json` | ship components; the 69 research projects: the tree, the boost lines and the biosphere of #91           |
| `subjects.json`                    | the eight research subjects in lane order: `{ id, name }`; every project names one in `subject`         |
| `regions/<group>.json`             | regions of a body with deposits and grades (see Regions below)                                          |
| `asteroids.json`                   | 59 real asteroids: orbit, size, mass, type (see Asteroids below)                                        |
| `reserves.json`                    | Earth's reserves of 43 materials (see Earth's reserves below)                                           |
| `environments.json`                | gravity, radius, temperature, water cover and air of the hand-made bodies and Ceres (see Suitability)   |

Ids are `snake_case` and unique across materials, buildings, components and recipes. Amounts are kg unless the material has a `unit` (`eflops` compute, `model` trained model). A recipe's `power` is kW while it runs, `hours` is the batch time, and `generates` is kW produced by a generator. Compute is a rate in EFLOP/s, never stockpiled: a recipe's `compute` input or output is EFLOP/s while it runs, whatever its `hours` (`COMPUTE` in `processes.ts`), while compute in a building cost is EFLOP/s hours drawn over the build. A data centre (`compute_generation`) makes 90 EFLOP/s at 120 MW; the figures that were in the old `cu` unit were converted at 1,000 cu an hour to 90 EFLOP/s, so a data centre stayed a data centre.

- **A material** is one record in the file of its category. `sources` lists where it is mined or collected: `{ body, how, building }`, with a `body` from `types.ts`, and a `building` of kind `extraction` that stands on that body. A material with no `sources` must be the output of a recipe. `tier` is `P` proven, `E` engineering-plausible, `S` speculative. `source` is a working URL.
- **A recipe** is one record in the file for its building. `research` is the number of the project that opens it (0: open from the start), and its building's project must be that project or one of its prerequisites. `estimated: false` means the ratio follows a balanced reaction or a standard composition that `reaction` states and `source` cites; the tests then check the mass balance to one percent. Everything else is `estimated: true`, and no recipe may create mass. `power` and `hours` are placeholders everywhere until the economy is tuned. `water` (with `waterSource`) is kilograms of water a batch the recipe draws from the stock while it runs on Earth, on top of its `inputs` (#82).
- **A project** (`research.json`) is `{ id, number, name, subject, tier?, rp, requires }`, and a boost level adds `line`, `level`, `effects` (an effect key to the factor at that level), `basis`, `source` and `estimated`. `requires` names lower numbers only, so number order is always a valid order. Every building, recipe and component names in `research` the project that opens it, and the project is complete: with only the tags of the project, of its transitive `requires` and tag 0, everything it opens can be made. `subject` is one of `subjects.json`.
- **The thin path** is `thin: true` on a record. Thin recipes, buildings and components may use only thin materials, and the thin records each project opens must be reachable on the thin path from its own prerequisites. Buildings with `start: true` exist on Earth at the start and are not paid for.
- Politics never restricts supply; scarcity comes from physics, geology and industry only.

`src/lib/game/data/data.test.ts` is the gate: unique ids, known references, every material extractable or produced, mass balance, the thin path closing on itself, everything a project opens made from its own ancestors' tags alone (thin path and whole set), the ladder of costs, the boost lines chained level after level, every project naming a known subject and every subject used, and no material, building, component or recipe stranded by a cycle. Add data, then run `pnpm exec vitest run src/lib/game/data` until it is green.

### Flight planning

`src/lib/game/flight/` is the movement rule of #8 as pure functions: SI units (metres, seconds, kilograms, m/s), float64, no Svelte, no globals, nothing wired into the game loop yet. Import from `#lib/game/flight/index.ts`. Time is game seconds (`game.elapsed`). It takes bodies as arguments (`FlightBody`: `gm`, `radius`, `orbit`, `angle`, `angularSpeed`, optional `parent`, `lowOrbitAltitude`, `atmosphere`), so it does not import the mock world; `reference.ts` holds real Sun, Earth, Moon, Mars and Jupiter constants for tests.

- **Engines**: `components.json` gives each propulsion component a `performance` record (`isp` s, `thrust` N vacuum, `thrustSeaLevel`, `mass` kg, `power` kW, `basis` flown, ground-tested or design-study, `source` URL). A `Ship` is `{ dryMass, payload, propellant, engine, count?, powerAvailable? }`; an electric engine's thrust is scaled by `powerAvailable / power` when that is given.
- **Rocket equation** (`rocket.ts`): `propellantForDv`, `dvFromMasses`, `shipDeltaV`, `massAfterBurn`, `burnTime`, `meanAcceleration`, `legBudget(ship, [dv1, dv2])` for out-and-back, `roundTripFeasible`.
- **Wells** (`wells.ts`): `surfaceToOrbit`, `orbitToSurface({ aero })`, `escapeFromOrbit(gm, r, vInf)` and `captureIntoOrbit(...)` with the Oberth effect, `lowOrbitRadius`, `circularSpeed`, `orbitalPeriod`.
- **Transfers** (`kepler.ts`, `line.ts`, `spiral.ts`): `hohmann`, `synodicPeriod`, `crossingTransfer` (departure burn tangential, arrival crossing the target orbit; reduces to Hohmann), `brachistochroneTime`, `burnFlipBurn`, `burnCoastBurn`, `solveLine` (moving target), `lineThresholdAcceleration`.
- **Planner**: `planTrip({ from, to, departAfter, ship, system, aerobrake? })` returns `{ options, reasons }`. A `Place` is `{ kind: 'surface', body }`, `{ kind: 'orbit', body, altitude? }` or `{ kind: 'point', id, primary?, orbit, angle, angularSpeed? }` (a jump point or station at fixed elements). Each `TripOption` has `profile` (`cheapest`, `balanced`, `fastest`), `model`, `departure`, `window`, `arrival`, `duration`, `dv`, `propellant`, `propellantLeft`, `canStop`, `canReturn`, `returnDv`, `aerobraked`, `maneuvers` (kind, mode, dv, duration, start) and `stamps`. `reasons` carries a code (`delta-v`, `thrust-surface`, `thrust-landing`, `no-path`, `same-place`, `unknown-body`) with `need` and `have`; when a ship can leave but not stop, one option with `canStop: false` comes with the `delta-v` reason.
- **Ship state**: `positionAt(option, t)` gives `pos`, `vel` (system frame), `phase` (`parked`, `departing`, `accelerating`, `coasting`, `decelerating`, `transfer`, `arriving`, `arrived`), `thrusting`. It is a function of absolute `t` only, so a 30-day step and thirty 1-day steps give the same position. `eventsOf(option)` lists burn starts and ends, the flip and the arrival.

Approximations, all deliberate:

- **Common primary.** A trip is planned around the deepest body both places orbit (Sun for planets, a planet for its moons). Moon-to-planet legs climb out stage by stage: escape the moon to zero excess speed, then escape the planet from the moon's orbit radius. Circular coplanar orbits only, prograde, no gravity assists, patched conics.
- **Ascent and landing.** Ideal energy cost `sqrt(2 gm (1/R - 1/(2 r)))` times `1 + 0.085` (gravity loss calibrated on the Moon's 1.87 km/s) plus the body's `atmosphere.ascentLoss` (calibrated net of rotation so Earth gives 9.4 km/s). Lift-off needs thrust-to-weight 1.2 on sea-level thrust; landing needs 1.0 at the final mass unless the body's air does it (`landingDv`). Aerobraking is `captureIntoOrbit` with `residualDv` instead of the burn, only below `aerobrake.maxVInf`, and only when `aerobrake: true`.
- **Orbit model (impulsive).** Burns happen at the periapsis of the parking orbit as up to 24 passes of at most 30 degrees of arc each, with a finite-burn loss of `arc^2 / 8` per pass (velocity-aligned thrust). More passes than that makes the leg a continuous spiral costing `vc + vInf`. If the thrusting at a planet spans more than 30 degrees of that planet's orbit, the whole trip becomes a spiral.
- **Spiral model.** Edelbaum tangential thrust between circular orbits, `|vc1 - vc2|`; position is `r = gm / v^2` with the swept angle integrated numerically. Valid while the acceleration is well below local gravity; the arrival velocity then has a radial part of about `2 a / g` of the circular speed (measured 9 percent for two NEXT thrusters on a 5.5-tonne ship going to Mars, 37 percent for eight). `TripOption.approximate` is true when `a / g` at the outer orbit exceeds 0.1.
- **Windows.** The target must lead the origin by the angle that makes the ship meet it: `sweep - omega_target * T`. Windows repeat at the synodic period. A ship parked at a planet departs from any phase of its parking orbit; the wait of up to one parking period is not added.
- **Fast transfers.** `crossingTransfer` raises the departure burn above Hohmann: faster, costlier, arriving across the target's orbit instead of tangent. It is only used while burns take at most 25 percent of the flight (impulsive assumption).
- **Straight-line model.** The primary's gravity is ignored. Thrust is constant at the mass-averaged acceleration of the burn, found by fixed point with the rocket equation; with a delta-v budget below the full burn it is burn-coast-burn. The target moves, so the flight time is solved by iterating the arrival point; arrival matches the target's velocity. Used only when `g(r_closest) * T / (a * t1) <= 0.05` (equivalently `a >= 2 g / 0.05` for a full burn, `lineThresholdAcceleration`: 0.24 m/s2 at 1 AU for the Sun), and the straight path stays outside the primary. Integrated under the Sun's gravity at the threshold the miss is 3.8 percent of the distance; at ten times the threshold it is 0.4 percent, at a tenth it is 30 percent (`line.test.ts`). The planner delays a straight-line departure up to one synodic period to clear the Sun.
- **Why the models are not compared at a boundary.** Hohmann minimises delta-v and the straight line minimises time, so for one ship they differ by orders of magnitude in both (259 days at 5.6 km/s against days at hundreds of km/s). What the tests check is each model against numerical integration of its own physics, and that a very fast crossing orbit reduces to a straight coast.
- **Profiles.** `cheapest` is Hohmann (or the spiral); `fastest` spends the ship's whole delta-v on whichever of the crossing family and the straight line arrives first; `balanced` is the same at the geometric mean of the two delta-v. `canReturn` plans the return from the arrival time with the propellant left and without aerobraking.
- **Positions.** The ship follows the primary-centred path from the origin level's centre to the target level's centre; during local burns it is on the place's own parking ring. Jumps between the two are at most a parking radius.

### The economy

`src/lib/game/economy/` simulates the data above. It is pure TypeScript plus one `.svelte.ts` for the live state, and it imports no screen; `screens/economy/system.ts` registers it as the `economy` system and owns the chips. `economy` (from `#lib/game/economy/index.ts`) is the one `Economy`: `sites`, `done` (project numbers researched), `running` and `queued` projects, `scientists`, `elapsed` and a mass `ledger`. Change it only through the actions in `actions.ts` and `programmes.ts`, then call `touch()`, which drops the cached `flowsOf(site)` that every screen reads.

- **A site** is a place with a stockpile (`stock`, kg or the material's unit), building `groups`, a construction `queue`, `population`, a workforce share and a `gridKw`. Its `body` is a data `Body`, which decides what can stand and be extracted there, and `worldBody` is the map body. Earth is the only site; a station, the Moon or an asteroid is another `Site` in `economy.sites`, and nothing else changes.
- **A group** is `count` buildings of one type running one `process`: a recipe, or `extract:<material>` for a material whose `sources` name that building on that body (`EXTRACT_KG_PER_HOUR` each, a placeholder, or the material's `extractKgH`: 1 kg an hour for gold, platinum, rhenium, indium, gallium, beryllium and tantalum; `extractRate(id)`). A recipe input its own building extracts where it stands (air at an air separation plant) is drawn from the environment. A group with no process is idle; one switched off runs at nothing. `assign(eco, site, group, process, count)` moves some or all of a group to another unlocked process.
- **Rates.** `siteFlows(eco, site)` gives every group a share of full rate: capped by workers (population times workforce share, shared out in proportion), then scaled down in proportion wherever an input has no stock and its consumers want more than its producers make. Power (`POWER`) and compute are never stockpiled, so they always balance this way: power plants, `gridKw` and generators against demand, data centres against recipes, builds and programmes. Food is counted in calories: every food material (`category: food`) has `kcalPerKg` with `kcalSource` and `kcalBasis` (wheat 3,270, potato 770, soybean 4,460, leafy greens 150, meat 2,200 estimated, single-cell protein 3,500 estimated, food ration 2,800 estimated: the ration is one packaged kilogram a person a day for the reference diet), and a person needs `kcalPerPersonDay` (2,800, the FAO, WHO and UNU figure for a moderately active man of 18 to 30; a `Site` carries it, new sites take Earth's). People eat from surplus first and stores second, shared out between foods by calories, so `flows.food` (`demand`, `made`, `eaten` in kcal an hour, `eatenBy` and `madeBy` per food, `cover`) is in calories while `flows.eaten`, `eatenMass` and the ledger stay in kilograms; cargo and stock stay in kilograms too (`kcalOf(id)` converts). Population grows `growthPerYear` (on a surface site times `growthScale(worldBody)`, Earth's suitability over its suitability at the start, 1 until warming changes) only while the calorie need is met and the site has a free berth (Earth's `berths` is `null`, so it always has), stops at `berthsOf(site)` (a segment ends when it fills them), and shrinks by `STARVE_PER_YEAR` times the shortfall when the need is not met. The Summary tab shows calories made by food as a bar against the need, each food's share of what is eaten, and a tile per food; the top bar's food chip is calories made against needed.
- **Time.** `advanceEconomy(eco, seconds, log)` integrates in segments that end at each game day, when a stock runs out, when a build finishes and when a project finishes, so a 30-day step gives the same totals as thirty one-day steps. The ledger counts kilograms extracted, eaten, built and lost in recipes; the stock change always equals extracted less the rest.
- **Construction** builds the first `BUILD_SLOTS` unpaused orders in queue order, spending each building's cost evenly over `buildHours` (placeholder: ten days plus two days a tonne); a short material slows it and is named on the order. A finished building joins the group with the same building and recipe.
- **Research** (#61, `programmes.ts`). The tree is `research.json`: 38 projects in the eight subject lanes, each costing a rung of Aurora's engine ladder by its place in its lane (30, 60, 120, 240, 360, 600, 1,200 RP; jump point stabilisation 240), ten boost lines of 30 levels whose `effects` act on booster thrust and propellant, shipyard points, build speed, mine output, research points a lab, semiconductor fab output, data centre compute, solar array output, battery storage and electrolysis power (`boostOf(done, effect)` is the factor of the highest level researched; the economy applies them in `boosted` and the yard and build actors, the ship parts in `shipdesign/boosts.ts`), and the Biosphere of #91 (600 RP, tier E), which opens the biosphere. A building, recipe or component tagged `n` opens when project `n` is researched (`isUnlocked(eco, item)`, `tagOpen(done, tag)`); tag 0 is open from the start, and `designStats` takes the same rule as a predicate over tags. `economy.scientists` are the sketch's six (`scientists.json`: name, gender, subject, skill 1 to 10, administration, portrait seed, birth year), `economy.running` the projects under way (`{ number, lead, labs, rp }`) and `economy.queued` each scientist's own queue: projects waiting for a busy lead, or for prerequisites under way. `createProject(eco, n, lead, labs)` starts a ready project (prerequisites researched) on its lead with labs capped by the lead's administration and the free labs (`labCap`, `freeLabs`), or queues it when the lead already leads one; a locked project whose missing prerequisites are all running or queued (`canQueue`, `missingRequires`) is queued whatever the lead is doing and shows as `waiting` until they are researched; `setLabs`, `cancelQueued`, and `startProgramme(eco, n)` (the best idle scientist for the subject at full labs, for tests and the test API). Labs are `research_lab` buildings on Earth (four at the start; `labsActive`); each lab on a project adds 1 RP a month times one plus the lead's bonus (0.08 a skill point in field, 0.02 out of it, `bonusOf`) times the research rate boost, and draws 18 EFLOP/s, 10 MW and 500 t of water a month (`lab` on the building record), so the project actor's share falls with a compute, power or water shortfall. A finished project logs `<name> researched.`, gives its lead a fixed 50% chance each of +1 administration and +1 skill (skill up to 10; `gainExperience`, seeded by scientist and project), and the lead moves on to the first queued project whose prerequisites are researched with the same labs; then every idle scientist does the same with the labs `labCap` allows. Labs switched off come off the newest projects first (`trimLabs`, each segment). The university stands as a building without figures or graduates; its figures and rules, lab wages, scientists' fields, retirement and booster recovery's cost are open on #61, #88 and #66.
- **The Research screen** (`screens/research/`) is where a project is created. A stat strip (researched, projects running and when the next finishes, labs assigned of active, compute to research and the share met, scientists and how many lead nothing) sits over four tabs, `?rtab=tree`, `programmes` (Projects), `unlocks` and `scientists`, and the card on the right. `Tree` is `#techTree`, a panel-wide scroller of subject lanes: one row band per subject of `subjects.json` with its glyph and name in a label column that stays in place (`SUBJECT_ICONS`), as many rows as the lane's fullest column needs (17 in all with the boost lines, so it scrolls up and down too), columns by prerequisite depth (`depthOf`), so every line runs left to right and early research is on the left. `chain.ts` is pure: `layoutChain` places the projects (tiles `TILE_W` by `TILE_H`, `GUTTER` between columns, `ROW_GAP` between rows, never scaled) and routes each prerequisite as an orthogonal line that leaves its source at the right edge, travels only in column gutters and the gaps between rows, offsets lines that share a gutter, and enters its target at the left edge; `chain.test.ts` checks that no line crosses a tile that is not one of its ends. Tiles are `wide` `Tile`s with the name and an icon (`projectIcon` in `gfx/icons/projects.ts`: the last building or part it opens, or the thing a boost line acts on). The mouse wheel scrolls it sideways when nothing scrolls vertically, dragging the background pans it, and a selected project is scrolled into view. Lines are amber when they leave a researched project and dashed and dim when not; the selected project, or the hovered one, shows the lines from its prerequisites in amber and to what needs it in teal on top, outlines those tiles the same way, and dims the rest. A tile is locked only while a prerequisite is not researched, and its tooltip names them. `?project=<n>` selects one, `&scientist=<id>` a scientist, and `&start=<n>` (repeatable) starts a project with `startProgramme`, for tests. `ProgrammeList` groups the projects as running, queued, waiting, ready, locked and researched. `UnlockList` shows what each project opens (`openedBy`: buildings, parts and the materials no other recipe makes) or, for a boost level, its effect. `ScientistList` is the portrait grid (`ScientistTile`: an `off` tile with the head, the name, the subject and skill or, on a project card, the bonus and lab cap, and what the scientist leads). `ProgrammeCard` follows the sketch's card: header with the status; RP, subject and, while running, RP a month; running: research points against the cost, time left, the lead with the bonus and `#programmeLabs` (minus, labs of the cap, plus, free labs); queued: the scientist and a cancel button; ready: the scientists sorted with the field first (`#programmeScientists`), the planned labs (`#programmePlanLabs`, not for a busy lead) and `#programmeStart`, Create project or Queue for <first name>; waiting: what it waits on (`#programmeWaiting`) above the queued row; locked: what it needs (`#programmeWhy`), and when `canQueue` holds the scientists and Queue for <first name> without planned labs; then the prerequisites as tiles, and what it unlocks or its effect. On the Scientists tab the card is `ScientistCard`: the bust, skill, administration, what the scientist leads and queues, and a button for each ready project to create or queue it for them. `checkFor` in `programme.ts` counts the prerequisites not researched and `programme.test.ts` checks that a project has none exactly when it is not locked. The top bar's labs chip (`screens/research/system.ts`) is labs assigned of active, red while one is free.
- **Power plants** (#76) are the ten buildings of `buildings/power.json`, each 1 GW with a `plant` record: `capacityKw`, `capacityFactor` (or `storageKwh` for battery and pumped hydro storage), `firmShare`, `co2PerMwh`, `waterPerMwh`. They stand only on Earth, take no process and no workers, and a group's `active` (absent means all) says how many run; `setActive` sets it and a finished plant joins the active ones. `gridOf(site, demand)` (`grid.ts`) makes the two checks: average generation (capacity times capacity factor) and firm capacity (capacity times firm share, storage included) against a peak of `PEAK_RATIO` (1.4) times demand; the plants supply the lesser of the average and firm capacity over 1.4, and `flows.grid` carries the figures. Demand is only the player's buildings. A short supply scales every powered building to the same share; firm capacity short of peak logs a warning (`alerts.firm`). Off Earth `gridKw` (a ship's solar power) and generator recipes (fission reactor, fusion plant, solar power station) add to the supply outside the checks. Summary shows a Power block (`PowerBlock`: generation by source against demand, capacity, firm against peak, storage in GWh), and a plant's Production card its figures and an Active stepper (`#plantActive`).
- **Water** (#82) is drawn on Earth (`WATER_DRAWN_ON`) by the recipes with a `water` figure, the design sketch's per building a month: the polysilicon fab 500,000 t, the IC fab 1,140,000 t, the flight machine shop 1,000 t, the data centre 157,788 t (216 t an hour); and by every active plant at its `waterPerMwh` of average output (`plantWater`: coal and oil 2.6 t, nuclear 2.5, bioenergy 2, gas 0.75, solar 0.1). `process(id, body).water` and `GroupActor.water` are the draw at full rate, and it is part of `inputs`, so it settles like any input: plants without water stop, and the power they made goes with them (`plantsRunning`). A Production card shows it as a Water row, apart from the recipe's inputs. Off Earth nothing draws it.
- **Earth at the start** is `src/lib/game/data/earth.json`: population, workforce share, kcal a person a day, growth, stock days and the groups. Its `sizing` block states the rule the counts follow: ranches (`ranch_meat`: 3 kg of cereal and soybean feed and a tonne of water for a tonne of meat, from the published figure of 2.8 to 3.2 kg of human-edible feed a kilogram of boneless meat; `estimated` water) make meat for about 10% of the calories, about 380 Mt a year against about 360 Mt in the world today, and farmland feeds the rest of the population with a 5% surplus in calories, end products run at present-day world output, each material with an Earth reserve is extracted at its 2024 world output (one mine for every 8,766 hours of its mine rate, oxides and ores converted to content, counts from `mockup/sketch/data/earth.json`), every other group feeds its consumers plus 10% (water included, with what the plants, fabs, machine shops and data centres draw: 1,843,831 mines against the sketch's 1,834,546), the power plants keep the 2024 mix and generate on average 5% more than start demand, and stocks start at 90 days of production. The goods are the exception: one semiconductor fab on polysilicon (`electronic_silicon_purification`, 2.5 t a month at 60 MW), one on radiation-hardened ICs (`rad_hard_ic_fabrication`, 1.2 t a month from 1.5 t of polysilicon a tonne and 36 EFLOP/s, at 80 MW), two flight machine shops (`machinery_machining`, 3 t a month from 0.6 t stainless steel, 0.3 t nickel superalloy and 0.2 t Ti-6Al-4V a tonne, 0.1 t lost as swarf, at 30 MW) and two data centres stand at the counts of the design sketch, and `startStock` gives 6 t of polysilicon, 30 t of machinery and 8 t of ICs in place of stock days. Machinery is its own category, `machinery`. Earth makes no silicon at the start, so the polysilicon line waits for it. Change a count and keep that rule, or change the rule there.
- **Money and contracts** (#84, `market.ts`). `economy.market` holds the `treasury` in dollars (starts at `START_TREASURY`, $15B), `paid`, the month, this month's `offers` and the signed `contracts`. A month is `MONTH_HOURS` (730.5 hours) of `economy.elapsed`; segments end at each month and at each contract's `due`. Each month `makeOffers(eco, month)` (seeded by the month, so a month always brings the same offers) makes up to three leases of the goods buildings and power plants of `earth.json` (5 to 20% of those running), up to three of the 14 largest other Earth groups of at least 20 buildings (0.5 to 2.5%), and with a chance of 0.6 each a supply contract of machinery or ICs (10 to 40% of a month's output at Earth, 1 t when it makes none); each lasts 3, 6, 6, 12, 12 or 24 months. A lease pays `LEASE_YIELD` (1.5%) of the building's `bp` ($1B a BP) a month times a demand of 0.6 to 1.6, so a building without `bp` is never offered; a supply contract pays the material's `price` (dollars a kg) times 0.8 to 1.5. `acceptOffer` takes leased buildings out of their Earth group (a group that empties is removed, and recreated when they come back); every month from signing a lease pays, and a supply contract delivers from Earth's stock and is paid, or is `missed` and not paid. Upkeep is a recipe's `upkeep`, dollars a month a building, given only to the fabs, machine shops and data centres of the sketch; switched-off and leased buildings pay none. At each month `paid` becomes `(treasury + lease income) / upkeep due`, at most 1: groups whose recipe has upkeep run at that share (limit `upkeep`) and only that share is charged, continuously. `marketLedger` is the coming month's leases, supply contracts that stock covers, upkeep and net. Taxes, wages, scientists, selling and buying are not built. The scripted player accepts the best paying power plant lease whenever 12 months of upkeep less lease income would overdraw the treasury and the grid keeps 3% above demand without the plants (`keepSolvent`).
- `?scenario=famine` halves Earth's farmland and empties its food stores at load, for tests. `?scenario=market` signs every offer of the first month; with `&broke` it signs none and empties the treasury instead.

### Regions, survey and asteroids

**Regions** (#15) are `data/regions/*.json` records `{ id, world, body, name, kind, known?, deposits: [{ material, grade }], basis, source, estimated }`, loaded by `data/regions.ts` (`regions`, `regionsOf(world)`, `atmosphereOf(world)`, `region(id)`, `depositGrade(world, regionId, material)`, `bodyTypeOf(world)`, `typeHolds`). `world` is a map body id and `body` its data type (`WORLD_BODIES` maps luna to `moon`, europa, ganymede, callisto and enceladus to `icy-moon`, the giants to `gas-giant` and `ice-giant`; an asteroid or data moon takes its type from `ASTEROID_BODY`, a comet is `comet`). A `ground` region is a named place a surface site can stand in; an `atmosphere` record is body-wide and reaches every region of its body (Mars, Venus, the four giants, Titan). Earth has no regions: `depositGrade('earth', ...)` is 1 and it stays one rich site. A deposit is a material that some building extracts on that body type (`data.test.ts` checks it, and that every source on a mapped body type is held by some region, so `reach` still closes: it takes a source as open only where a region of that type holds the material).

- **Grade** is a relative richness index from `GRADE_MIN` 0.05 to `GRADE_MAX` 4: 1 is the nominal 1,000 kg an hour of the extractor, and a deposit of grade 2 yields twice that for the same power. Every region is `estimated: true`; its `basis` gives the real figures (LCROSS 5.6 percent ice at Cabeus, Lunar Prospector thorium, MESSENGER sulfur, Dawn ice and organics on Ceres) the grades are scaled from, and `source` a URL.
- **Extraction by region.** `Site.region` is the region id for a surface site off Earth and `null` for Earth and for an orbital site. `gradeAt(site, material)` is the region's grade, the atmosphere's for an atmospheric source, 1 on Earth and `undefined` where the region lacks the material or the site is in orbit (orbit extracts nothing from the ground). `unlockedProcesses` and `firstBuildings` list only processes whose materials the region holds, so an ice mine cannot stand in the maria; a group whose region cannot supply its material runs at nothing with limit `deposit`. An `extract:` group's outputs and extracted mass are multiplied by its grade and the `GroupActor` carries `grade`; the grade pill on a Production card and the Summary tab's Region block show it. A site is unique per body, place and region: `newSite` takes `region`, the first surface site keeps the body id and later ones take the region id, so a second site may stand in another region of one body.
- **Earth's reserves** (#64) are `data/reserves.json` records `{ material, reserve, basis, content, output, accessibility, source, estimated }` from `mockup/sketch/js/minerals.js`: `reserve` is the published figure in kg in its `basis` (USGS Mineral Commodity Summaries 2025, the NEA Red Book 2024 for uranium, OPEC's Annual Statistical Bulletin 2025 for natural gas and crude oil; `estimated` where USGS gives no world figure), `output` the 2024 world output in kg a year, `accessibility` 1 everywhere and not used by the simulation. `content` is the kilograms of the material the reserve holds: the reserve itself where the basis is already content, and for a reserve in ore or oxide terms (bauxite, chromite ore, phosphate rock, K2O, TiO2, ZrO2) the reserve times the share its mine count takes of world output, so years left is the published reserves-to-output ratio. Ilmenite and the rare earths, which Earth does not mine at the start, have `content: null` and are not drawn down. Extraction at Earth's surface site draws `economy.drawn[material]` against `content` (`reserveOf`, `finiteContent`, `reserveLeft`, `isReserveSpent`); the economy ends the segment when a reserve runs out, every group extracting it becomes `depleted`, and an event is logged. Water and ethylene have no reserve.
- **Depletion of a whole body applies to asteroids and comets only** (`depletableRecord`). All extraction at a surface site on one draws down `economy.mined[body]` against the body's whole mass (`remainingMass`); the economy ends the segment at the moment the mass runs out, the group's limit becomes `depleted`, `economy.exhausted` lists the body and an event is logged. Ceres follows the same rule but its mass makes the limit unreachable; planets and moons are never depleted.
- **Survey.** `game/survey.svelte.ts` holds `survey.levels` (world id to 0 or 1; `resetSurvey()`). Every region is unknown until its body is surveyed except where the record says `known: true`: the Moon (all four regions, because Lunar Prospector, Clementine, Chandrayaan-1, LRO and LCROSS mapped it from orbit and sample return covers its main rock types) and every atmosphere (spectroscopy and probes). Mars, Mercury, Ceres, the asteroids, comets, small moons, dwarf planets and the icy moons start unknown. The order `survey` (`{ type: 'survey', body }`) needs a ship whose design carries the `survey_suite` component (`surveys: true` in its design, opened by Remote-sensing instruments, estimated, sized after the Lunar Reconnaissance Orbiter payload), in orbit of the body (free in orbit or docked at its orbital site), for `surveyDays(world)` days (`SURVEY_DAYS_PLANET` 60, `SURVEY_DAYS_SMALL_BODY` 14 for a body under 1,000 km across, placeholders); then `completeSurvey` marks the body done, the regions appear and the log says so. A body without ground regions (Venus, the giants) has nothing to survey. Grades are shown to a first precision: `gradeView` gives a range `low to high` that holds the true grade, wide by `SURVEY_ERROR` 0.3, stable for a region and material; a site's own Economy view shows the exact grade.
- **Founding.** `foundOptions(v, region)`, `foundRegions(v)`, `needsRegion(v)` and `foundSite(game, v, building, region)`: a ship on the ground of a body with ground regions must name a known region with no site yet, and only buildings that can work in it are offered. A `land` order and a trip destination may carry `region`; a vessel that lands in a region with a site arrives at that site.

**The Sol catalogue** (#13): every body is a record with real figures from JPL, and the 15 hand-made bodies of `mock/bodies.ts` (the planets, Luna and the six large moons the economy, regions and tests name) stay in code with their look. Records keep a `source` URL. Missing numbers are estimated and flagged, never invented; a body JPL does not resolve, or gives no size or magnitude for, is left out.

- **Asteroids and dwarf planets** are `data/asteroids.json` records from JPL's small-body database (`https://ssd.jpl.nasa.gov/tools/sbdb_lookup.html`): `{ id, number?, name, type, typeBasis?, spectral?, dwarf?, a, e, diameter, diameterEstimated?, mass, massEstimated?, rotation, rotationEstimated?, source }` with `a` in AU, `diameter` in km, `mass` in kg: 488 records, ten of them `dwarf` (Ceres, Pluto, Eris, Haumea, Makemake, Quaoar, Orcus, Salacia, Sedna, Gonggong). `groupOf` sorts them into near-Earth (perihelion under 1.3 AU: 17), main belt (266), Hilda (5), Jupiter Trojan (37), centaur (17) and trans-Neptunian (146). An unnumbered body has no `number`; its angle hashes its id. `type` is carbonaceous, stony, metallic or icy and maps to `asteroid-c`, `asteroid-s`, `asteroid-m`, `icy-moon`. It comes from the Tholen or SMASS class (X-types follow Tholen: M metallic, P carbonaceous); without a class, `typeBasis: 'albedo'` (under 0.1 carbonaceous, else stony; beyond 30 AU carbonaceous under 0.1, else icy) and without albedo `typeBasis: 'assumed'` (stony, or icy beyond 30 AU); a dwarf planet beyond Neptune is icy. No near-Earth asteroid is metallic here: Amun, once taken for the metal one, is now classed D or C by its infrared spectrum, and 1986 DA's class is not given by the database. `mass` is from the database GM (or, for Ceres, Pluto, Eris, Makemake and Haumea, the JPL planetary table) unless its sigma is over 30 percent; otherwise `massEstimated` from the diameter and a bulk density of 1.4 (carbonaceous), 2.7 (stony), 4.0 (metallic) or 1.5 (icy) g per cu cm. `rotation` is the rotation period in hours from the database (`rot_per`, from the Lightcurve Database and spacecraft results), known for 393 of the 506 asteroids and comets; without it `rotationEstimated` is the median of the known periods of records in the same diameter range (7.67 h under 1 km, 11.08 h to 10 km, 10.18 h to 50 km, 11.45 h to 200 km, 7.81 h above). A missing diameter is `diameterEstimated`: `1329 / sqrt(albedo) * 10^(-H/5)` km, with the albedo JPL gives or an assumed 0.06 (carbonaceous), 0.25 (stony), 0.14 (metallic), 0.09 (beyond 30 AU) or 0.10.
- **Moons** are `data/moons.json` records from JPL's planetary satellite tables and Horizons: `{ id, code, name, planet, type, irregular?, aKm, e, period, diameter, diameterEstimated?, mass, massEstimated?, rotation?, rotationEstimated?, source }` with `aKm` in km and `period` in days: 65 moons of Mars (2), Jupiter (15), Saturn (18), Uranus (17), Neptune (8) and Pluto (5). `planet` is the body id of the parent (a dwarf planet can be one). A moon is `irregular` beyond 5 million km of Jupiter, 8 of Saturn, 2 of Uranus and 6 of Neptune; irregular moons and the Martian moons are carbonaceous, the rest icy. `mass` is from GM; without it `massEstimated` at 1.5 g per cu cm. Only irregular moons carry `rotation` (hours): Phoebe 9.2735 (Cassini) and Himalia 7.7819 measured, the rest `rotationEstimated` by the asteroid rule; a regular moon turns once an orbit. Diameter is twice the mean radius, from the satellite table or Horizons, else from the V(1,0) magnitude and an assumed albedo of 0.04 (`diameterEstimated`). A moon whose id an asteroid already holds takes the planet as a suffix (`metis-jupiter`, `pandora-saturn`).
- **Comets** are `data/comets.json` records: `{ id, designation, name, a, e, diameter, mass, massEstimated: true, rotation, rotationEstimated?, source }` with the nucleus diameter from JPL and the mass always estimated at 0.5 g per cu cm (67P measured 0.53). Comets with no nucleus diameter, and one on a hyperbolic orbit, are left out. Their body type is `comet`; the region template in `regions/comets.json` holds water, comet ice, carbon dioxide and ammonia.
- **Map bodies.** `game/asteroids.ts` turns an asteroid record into a map `Body` (circular orbit at `a`, `angularSpeed` from Kepler's third law, `angle` from a hash because the real phase is not modelled: **estimated**); `game/moons.ts` places a moon on a circular orbit of `aKm` around `parent` with its real period, and `game/comets.ts` a comet like an asteroid, so an eccentric comet moves on a circle of its semi-major axis. `isNearEarth` is perihelion under 1.3 AU. Every record has one region `<id>-body` generated from the template for its type in `regions/belt.json` (carbonaceous: chondrite, water, carbon, phosphorus; stony: chondrite, iron, Fe-Ni metal, nickel, silicon; metallic: Fe-Ni metal, iron, nickel, cobalt, platinum group and gold; icy: water, comet ice, ammonia); Ceres has three regions of its own. The map's decorative belt dots remain as the uncatalogued mass.
- **On the map**, a small body (a data asteroid, moon or comet) is a one-pixel mark below 2.5 px of radius. `drawMap` keeps its static facts between frames, computes its position from `phase + omega * elapsed`, and skips it altogether when it is off screen. It is named only when selected, aimed at, drawn as a sphere, a near-Earth asteroid below 1.5e9 m a pixel, or its diameter in km is at least a quarter-millionth of the metres a pixel (110 km in the belt view); a moon is hidden while its parent is a mark, or overlaps its parent as drawn, unless that parent is capped as a backdrop: then the moon is drawn in front of it, as a station is (`tests/map.spec.ts` zooms into the Moon and Mimas). Marks nobody names are returned as `MapFrame.marks`, used only to pick with the pointer. The zoom limit reaches the farthest body, but the System preset frames Neptune's orbit (`planetExtent`) and the Inner view stops at 3.5 AU. Layout states for a giant with its moons are `zoom=saturn:5e6` and `zoom=jupiter:4e6`.
- **Lists.** The Bodies tab lists the planets, then the moons in a `<details>` per planet, then the asteroids with a filter (all, dwarf planets, each group, each class; `#rockFilter`) and the comets. The Ships tab's trip destination and survey body are two selects: a group (`bodyGrouper` in `screens/economy/bodyGroups.ts`: planets, moons of each planet, dwarf planets, asteroids by group, comets; plus sites and jump points) and the places in it (`#tripGroup`, `#tripTo`, `#orderSurveyGroup`, `#orderSurvey`).

### Suitability and biospheres

**Environments** (#91) are `data/environments.json` records `{ world, gravity, radius, temperature, water, atmosphere, warming?, niche?, basis, source, temperatureSource?, waterSource?, nicheSource?, estimated }` for the 15 hand-made bodies and Ceres, loaded by `environmentOf(world)`: gravity in m/s2, radius in m, mean surface temperature in K, water cover as a share, and the atmosphere as kilograms of gas materials (`nitrogen`, `oxygen`, `carbon_dioxide`, `methane`, `argon`, `helium4`, `hydrogen`, `ammonia`; each gas carries `molarMass` in g/mol). Figures are the NSSDC fact sheets' where they give them (Mars at the 210 K the fact sheet gave until 2021) and Wikipedia's otherwise; a fact sheet's air mass is split into gases by volume share times molar mass, and gases with no material (neon, krypton, CO, SO2) are left out. Titan's air mass is its pressure times its surface over its gravity (`estimated`). Earth also carries `warming` (+1.4 C at the start) and `niche`, the share of people inside the human climate niche against warming (Lenton et al. 2023: 1, 0.91 at +1.2, 0.667 at +2.7, 0.5 at +4.0 C, held beyond).

**Suitability** (`game/suitability.ts`): `suitability(world, warming?)` is `{ habitable, cc, s, factors, gravity (g), pressure (atm), temperature (C), water, lowGravity }`, or nothing for a body without a record. Colony cost is the worst single factor, never a sum: oxygen partial pressure outside 0.1 to 0.3 atm or above 30% of the air (2), a dangerous gas above its limit by mole fraction (NH3 50, CH4 500, H2 500, CO2 5,000 ppm: 2), pressure above 4 atm (2, and 2 × P ÷ 8 above 8 atm), water cover under 20% ((20 − %) ÷ 10), temperature outside −10 to 38 C (1 per 24 C), gravity under 0.1 g (1). Pressure is the stock's mass times gravity over the surface. Earth's temperature term is `1 / niche share − 1` at its warming. Gravity above 1.9 g or a giant makes a body uninhabitable (`s` 0). `s = 1 / (1 + cc)`: Moon 0.33, Mars 0.31, Mercury and Callisto 0.16, Titan 0.12, Earth 0.878. `growthScale(world, warming?)` is `s` over `s` at the start, 1 on any body without a niche.

**The biosphere** (`buildings/habitat.json`, opened by project 69, `where` the Moon, Mars, Mercury, icy moons and carbonaceous and stony asteroids) holds `biospherePeople(world)` = floor(300 × `s`), halved under 0.1 g: 100 on the Moon, 93 on Mars, 47 on Mercury. Its `biosphere` record gives `people`, `powerKw` 83, `volume` 6,700 m3, `shell` 406 t, `shield` 8,500 t and `shieldMaterial` by body type (lunar regolith, Martian regolith, basalt, carbonaceous or ordinary chondrite, water), with the sources of each. Its cost is the inflatable habitat's materials scaled to the shell and 17 life support units; `buildCost(id, where)` adds the shield of the body it stands on, so the build time follows. It stands only where `biospherePeople` is above 0 (`holdsHere`), draws 83 kW and nine workers (its group actor), and its berths count whether it runs or not. `berthsOf(site)` is `null` on Earth, `berths` plus the biospheres' capacity on a surface site, and `berths` (installed modules) on an orbital or jump point site. The People tab shows the suitability of a surface site's body and what one biosphere holds there.

### Ships, launches, sites and supply

`src/lib/game/ships/` (import from `#lib/game/ships/index.ts`) holds the ships the player owns. `ships` (a `$state`) has `vessels`, `launches` and counters; `resetShips()` clears it. It reads `classes` (designs), `economy` (stock, sites) and `flight/` (trips), and a vessel is not a mock `Fleet`. The `economy` system (`screens/economy/system.ts`) calls `advanceShips(game, dt)` after the economy, so a vessel built that tick appears in the same step.

- **Build.** `orderShips(site, designId, n)` queues a locked design with no errors at a site that has its yard (`rocket_factory` on Earth; `orbital_shipyard` opens with the Orbital shipyard project). Components are folded into the ship's cost (`designStats(design).cost`), never a separate component build. Ships are built on shipyard points (`economy/yard.ts`): each shipyard of the design's yard type at the site makes `SP_PER_SHIPYARD_DAY` (1) SP a day, a design needs `shipyardsFor(dryMass)` = max(1, ceil(dry mass / 100 t)) shipyards and costs `shipPoints(dryMass)` = (`SHIP_BASE_DAYS` 2 plus `SHIP_DAYS_PER_TONNE` 0.5 a tonne) times that count in SP. An order is refused when the site has fewer shipyards than it needs. Each order has a `percent` of the site's SP (a new order takes the unallocated rest, `setShipPercent` keeps the sum at most 100, SP nobody uses is lost). `startShips` (run by the economy each segment and by every yard action) gives free shipyards to unpaused orders above 0%, paid ones first, then in queue order, and pays an unstarted order's whole cost from stock when it gets them; one short of a material waits and is named (`stalled`). Only orders holding their shipyards progress. `moveShipOrder`, `pauseShipOrder` and `removeShipOrder` reorder it. A finished ship is delivered to `economy.delivered` and becomes a vessel at that site with empty tanks and an empty hold. **Placeholder, estimated:** the SP figures; no workers or power are drawn.
- **A vessel** is `{ id, name, design, at, trip, propellant, cargo, crew, orders, run, progress, blocked }`. `at` is `{ kind: 'site', site }` (docked or landed at an economy site), `{ kind: 'orbit', body, angle }` (free in low orbit) or `{ kind: 'surface', body }` (landed with no site). `propellant` is kilograms by `PropellantKind`, `cargo` kilograms by material, `crew` people taken from a site's population. `vesselShip(v)` is what `planTrip` takes (the main drive, the cargo as payload, the other propellants as dead mass).
- **Launch.** `planLaunch(game, site, { ship, cargo? })` and `launch(...)` take one ship that stands at a site with a `launch_site` building and a free pad. Its tanks are topped up to its design `load` and its boosters filled from the site's stock by the propellant's mix, and the cargo is taken from stock into its bays (a short material or a full bay is a reason). The climb is `climbFrom` with the ship's propellant after the top-up, `v.boosters` boosters (the design's count on a built ship, 0 once launched; `boostersLeft`) and its cargo; a ship short of orbit or of thrust is refused with the numbers. The ship becomes a vessel in orbit at angle 0 with the climb drive's `leftover`, its other propellants and its cargo, and its boosters are dropped and lost. `payloadCeiling(game, site, ship)` is the most payload it lifts, up to its free bay; `designCeiling(design)` is the same for a design with an empty hold. A launch record holds the ship's name, the boosters dropped, the payload, the propellant burned and `perTonne` (propellant a tonne at the ceiling, which `importCost` reads). Launch sites have a launch rate: each `launch_site` building takes one launch per `PAD_TURNAROUND_DAYS` (`site.launches` holds when each pad is free again). **Placeholders, estimated:** `PAD_TURNAROUND_DAYS` is 4; the launch is instant in game time.
- **Landing and ascent from the same body** (`hop.ts`): the planner has no path between a body's orbit and its own surface, so a `land` order from orbit of that body (or docked at its orbital site) is a descent of `orbitToSurface` delta-v and a `fly` order from its surface or a surface site there is an ascent of `surfaceToOrbit`, each an hour (`HOP_SECONDS`, placeholder), checked for delta-v and thrust to weight (1.0 landing, 1.2 lift-off) and burning propellant. The flight library's own formulas make this almost free on a small body: 0.19 m/s on Bennu, 9.7 m/s on Eros, about 315 m/s on Vesta, 430 m/s on Ceres, 1.87 km/s on the Moon.
- **The flight model covers every map body with a reference**: Mercury, Venus, Mars, the giants, Io, Europa, Ganymede, Callisto, Titan, Enceladus and every data asteroid, dwarf planet, moon and comet (`gm` from the record's mass, a parking orbit at `min(100 km, radius)`; `FLYABLE` lists them all, `LANDABLE` all but `NO_SURFACE`). Venus and the giants cannot be landed on (`LANDABLE`); Venus's and Titan's atmosphere constants are placeholders.
- **Trips.** `planVessel(game, v, destination)` calls `planTrip` from the vessel's place with the game's own bodies (`flightSystem(game)` (cached per game and `game.elapsed`) turns the world bodies into `FlightBody`s with the reference constants (or the record's mass and size) and the world's orbits and phases, so a trip and the map share one set of positions at `game.elapsed`). It returns the options that can stop (window, duration, delta-v, propellant, propellant left, whether it can return) or the reasons it cannot go in words. A ship leaves a surface site that has a launch site and air by launch only (`leavesByLaunch`). `commitTrip` takes the propellant at once and `vesselState(game, v)` follows `positionAt`, so a 30 day step and thirty one day steps give the same position and arrival. A landing needs legs rated for the ship, or a heat shield rated for it on a body with air.
- **The jump point** is the `JumpPoint` of the system (`game.jump(id)`, `surveyed`, `stable`). The flight model gets it as a fixed `point` place (`jumpPlace`, static at the map position, so a ship matches rest there); a vessel at it is `{ kind: 'orbit', body: <jump id> }`, and `fly` takes the id as its body. A `survey` order at the point (`JUMP_SURVEY_DAYS` 30, placeholder) needs a ship with a survey instrument and marks it surveyed. `foundSite` at the point (refused until it is surveyed) makes a site with `place: 'point'` and `where` `jump-point` (id the jump id) whose first building is one of `data_centre` and `jump_point_stabiliser`; other ships `dock` there from the point. A data centre may stand there, since the stabiliser's 10 million compute units are made where it stands. A stabiliser at the site and Jump point stabilisation researched marks the point stable and logs that it is stable (`jump.ts` `settleJumps`, run by `advanceShips`). Nothing travels through it. The map labels it unsurveyed, unstable or stable and selects it.
- **A platform at a giant.** A ship in orbit of a body it cannot land on (`NO_SURFACE`: Venus and the four giants) founds a site with `place: 'surface'` that hangs in the air: ships `dock` to it from orbit, it counts as an orbit place for trips, and it extracts the atmosphere's materials (the scoop at Jupiter, Saturn, Uranus or Neptune, the skimmer at Venus).
- **Orders** (`orders.ts`): `fly` (to a body's orbit), `land` (on a body's surface; the vessel is at the site there if one exists), `dock` (from the orbit of a site's body into the site, one hour), `load` and `unload` (cargo by material, propellant by kind, or crew, four hours, the amount or all that fits), `wait`. `goTo(v, site)` adds the orders that reach a site. Orders run in sequence inside a step at their own times; a blocked order keeps its place and the vessel's `blocked` says why. Docking ignores the angle between a ship's orbit and a station's (**placeholder**).
- **Sites off Earth.** An economy `Site` has `place` (`surface`, `orbit` or `point`), `angle` (its orbit phase), `berths` (people it can house; `null` on Earth), `launches` and a `yard` queue beside its stock, groups and construction queue, and runs the same flows as Earth. `foundSite(game, v, buildingId)` turns a ship in free orbit or landed with no site into a site (`orbit-<body>` or the body's id): the ship's cargo must hold the building's cost, which is spent, and the building stands at once; the rest of the cargo and the propellant go into stock, the crew become the population, the ship's berths become `berths` at an orbital or jump point site only (`addsModuleBerths`), its solar power becomes `gridKw`, and the ship is consumed. One orbital site and one surface site a body. `installModule(game, v)` does the same for a ship docked at an existing site. A new site takes Earth's `growthPerYear`, so its population grows while it is fed and has free berths, up to its berths; people eat the site's food stock, so a station starves unless food is delivered or made. Colonists are people loaded as crew from a site's population (`load` crew, up to the ship's berths) and unloaded into another site's population, up to its free berths (counted from the population as shown, rounded); a ship installed with `installModule` adds its berths at an orbital or jump point site, and a surface site off Earth houses people only in its biospheres (`berthsOf`; see Suitability and biospheres). The crew of a ship that founds or is installed at a surface site still join its population without a berth, and the population does not grow until a biosphere gives it room. Buildings stand only where their `where` allows. **A stage's building needs are met by a building standing at any site**, so an orbit-only building (a propellant depot, a life support plant) is satisfied by a station.
- **Make or import** (`supply.ts`, the Supply tab): `supplyRows(game, site)` lists what a site off Earth wants (inputs of its groups, builds and programmes, and its people's food) with what it makes, its stock and, for each other site with stock, `importCost`: the propellant a tonne costs by the best freighter design the player owns (a round trip with a full hold from `planTrip`), or by launch (the last launch's propellant for a full load) from a surface site with air. `startRun(game, v, { item, amount, from, to })` sets a vessel's orders to the cycle `load propellant, load cargo, go, unload, come back` and repeats it (`v.run`); it is refused from or to a launch site. `clearOrders` stops it.
- **Founding the first station by play** needs the first building to be one research has opened: from the start a station can start with a chemical plant, an alloy works and the other buildings open from the start, and after Propellant transfer in orbit with a propellant depot. The player has no power in orbit before Space solar arrays, so a crewed ship (any crew or habitat part draws power) cannot be locked before the solar array is open.
- **Fuel cell, sample and landing drive.** The `fuel_cell` component lets a crewed design be locked once the crew capsule is open (a power-deficit warning gives its hours). A `sample` order (`ships/sample.ts`: `SAMPLE_KG` 1, `SAMPLE_DAYS` 2, placeholders) takes the first deposit of an asteroid's region into the hold of a ship in orbit of or on it with a `sampling_arm` (`samples: true`) and room; unloaded at a site it is ordinary stock. A landing or an ascent uses the drive with the most thrust that the ship holds propellant for (`hopShip`, `Hop.fuel`), so a ship on ion thrusters that also carries one chemical engine and a tank can land on an asteroid that pulls 1 kN on it, burning the chemical propellant and leaving the xenon.

## Saving

A save holds everything the simulation changes, so a loaded game runs on exactly as the original. `#lib/game/save.ts` is the codec: `serialise(game)` returns a `SaveData` (`SAVE_VERSION`; the clock and step, the event log, every body's orbit angle, each jump point's `surveyed` and `stable`, the whole `economy` with its treasury, offers and contracts, `ships`, the trip options of ships in flight with each flight system stored as its body angles, the `classes` registry and its id counter, and `survey.levels`), `checkSave(raw, game)` gives the reason a value cannot be loaded (another version, or a part missing), `resetGame(game)` puts all of it back to the start, and `restore(game, data)` resets and then applies a save, dropping the derived caches (`touch()`, the flight system and supply caches). A new module-level `$state` that the simulation mutates goes into `SaveData`, `resetGame` and `restore`, and `save.test.ts` (`PathPlayer` to stage 6 with research running, a ship on its way to the Moon with an order queued, a save, a reset, a restore and 30 more days on both) must stay green. Mock fleets, contacts and world sites, the officers, ground forces and intelligence of the mock screens, and screen state other than the screen, the Economy tab, site, ship and rate period and the Research selection and tab are not saved; research and scientists are part of `economy`, so they are.

The shell keeps saves in IndexedDB (`space4x`, store `saves`) the way Fantasia4x does (`shell/saveManager.ts`): each save is a slot of `save:<id>` (the state without classes and log, plus the UI), `classes:<id>` and `log:<id>` (written only when they changed since the slot's last write) and `meta:<id>` (game date, projects researched, sites, ships, when, `auto` or `manual`). The running game autosaves into its active slot (`scheduleSave`: after a game day or a class edit, at most once every `AUTOSAVE_GAP_MS`, in an idle callback; `saveGameNow` on `pagehide`, with the transaction opened at once and committed). A manual save is a new slot or overwrites one; loading an autosave continues in that slot, loading a manual save starts a new one so the snapshot stays. A game that has not moved since the page opened writes no slot. On `beforeunload` with progress since the last write, the game is saved when autosave is on and the browser asks before leaving when it is off. `shell/session.svelte.ts` is the game side: `startSession` loads the newest slot at startup unless the URL carries a test or scenario parameter (`check`, `test`, `scenario`, `reached`, `new`, `surveyed`, `outpost`, `asteroid`, `bench`), in which case nothing is loaded or autosaved; a slot that fails `checkSave` is deleted and an event says why. Without such a parameter the game opens on the main menu (`MainMenu`, shown while `session.title`; `?menu` shows it on a test link too): the title in the promo thumbnail's style (Pixelify 700, white with "4X" in #ffb43b, a hard black outline; its C is drawn as an SVG on the font's grid because Pixelify's bold C closes into an O) over the approved mockup's zoom view at Sol Station (`mockup/scenes`, `?z=10#zoom`): `sol-station.png` is its frame at 1440x900 without the station (720x450 pixels as the mockup's framebuffer held them, before the vignette), and `menuScene.ts` draws the map's `YardScene` on it at the mockup's scale and light, 30 frames a second, at two screen pixels a pixel or the next whole multiple that covers the window, centred, and Continue (when `session.resumable`: a save was loaded at startup or the player came back from the pause menu), New game (closes the menu on the fresh game when there is nothing to continue, otherwise `startGame('new')`), Load game and, in the desktop shell, Quit. Keys other than the buttons' own do nothing under it. `startGame('new' | 'load', entry)`, `saveGame()`, `overwriteSave(id)` and `flushSave()` are the actions. The autosave switch is `prefs.autosave` (`shell/uiPrefs.svelte.ts`, in `localStorage`). Escape or the gear opens `PauseMenu` (pauses, resumes on close): Resume, Save game and Load game (`SaveListMenu`, one `SaveListRow` a slot, with delete and overwrite confirmed in the row), New game, Autosave, Panels and Main menu (`openTitle`: pauses, autosaves, shows the title). `tests/save.spec.ts` (game project) reloads, saves, loads (a scripted game at stage 6 through the `?test` API's `snapshot()`, exactly), autosaves on the timer, warns before an unsaved close and drops a save of another version.

## Adding a system

A system is a function `(game, dtSeconds) => void` that `game.advance` calls on every tick. Put a screen's simulation in `src/lib/screens/<id>/system.ts`:

```ts
import { registerSystem } from '#lib/game/index.ts';
import { projects } from './projects.svelte.ts';

registerSystem('research', (_game, dt) => {
  for (const p of projects) p.done = Math.min(1, p.done + p.rate * dt);
});
```

`screens/index.ts` loads every `screens/*/system.ts`, so nothing shared needs editing. Registering a name again replaces the earlier function. Systems run in the order they are registered; `orbits` and `contacts` run first; `economy` runs the economy and then the ships. Test a system with vitest by building a `new Game()` and calling `advance`.

## Adding a screen

Each screen owns exactly one folder, `src/lib/screens/<id>/`. Replace its placeholder `Screen.svelte`; put its components, drawing code, mock data and system in the same folder (or its mock data in `game/mock/<domain>.ts`). Do not edit another screen's folder or the shared files to make room for yours; if a shared primitive is missing something, extend the primitive.

A grid screen's root is `ScreenGrid`, which renders `<main class="screen" data-screen="<id>">` straight under `#stage`, where the layout check looks for it:

```svelte
<ScreenGrid id="economy" columns="320px minmax(0,1fr)">
  <Stack>
    <Panel title="Colonies"><Table head={['Colony', '>People']} {rows} /></Panel>
    <Panel title="Mars" grow body="col"><CanvasView scale={2} bg="stars" draw={drawPlanet} /></Panel>
  </Stack>
  <Stack>...</Stack>
</ScreenGrid>
```

Only the map stays mounted when another screen is shown; any other screen is mounted when it opens and dropped when it closes, so state that must survive a switch lives in a module-level `$state` in the screen's folder. A screen's URL parameters are applied once at load, not when the screen mounts: export an `applyXParams(params: URLSearchParams)` from the screen's state module and call it from `screens/params.ts`. After that the module state wins, so a button that sets that state and then opens the screen (`showColony(id)`, then `shell.setScreen('economy')`) is not overridden.

## Icons, tiles and formatting

The management screens are built from icon tiles and cards, not text tables. The look is `mockup/ui/`; what it needs is below, so read this instead of the mockup's code. Everything is exported from `#lib/ui/index.ts` (components, `fmt`, tooltip helpers) and `#lib/gfx/index.ts` (icon functions). `/dev/tiles` (gallery build) shows every primitive and the whole icon set; `tests/primitives.spec.ts` covers it.

### Icon functions (`src/lib/gfx/icons/`)

- `materialIcon(id)`, `buildingIcon(id)`, `componentIcon(id)` return a PNG data URL, rendered once and cached. Sizes: materials and components 16 by 16, buildings 24 by 20 (`ICON_SIZE`). Draw them with `image-rendering: pixelated` at whole multiples; `PixIcon` does it.
- `IconRef` is `{ kind: 'material' | 'building' | 'component', id }`; `iconUrl(ref)` and `iconSprite(ref)` (`{ url, width, height, pixels }`) take one.
- The pixels are the mockup's, checked id by id against it (`icons.test.ts`, fixture `mockup-hashes.json`). A material's shape follows its category, its colour and two-letter mark come from tables in `materials.ts`; a material in the data without a colour gets the mockup's generated hue.
- An id the tables do not know is never blank. A material the data holds is drawn by its category; an id not in the data is a grey orb; a building is a hangar and a component a box, tinted by its `kind`. `hasIconArt(ref)` is false for those, and `icons.test.ts` lists them (today: the booster, the biosphere, the research lab and the university; the three nuclear fuel materials list the colour the mockup generated for them, because a generated hue follows a material's index in its category). Draw a new id in the generator file, add its hash to `mockup-hashes.json` only if the mockup has it, and the list in the test shrinks.
- `materialLook(id)` gives `{ base, R, shape, code }` (the colour ramp, for bars coloured like the material). `CATEGORY_NAMES`, `CATEGORY_ORDER`, `CATEGORY_EXAMPLES` (one material per category), `BUILDING_KIND_NAMES`, `COMPONENT_KIND_NAMES`, `KIND_COLOURS` (the stripe colour of a building or component kind) and `KIND_EXAMPLES` are the vocabulary for filters and headings; `categoryName(c)`, `buildingKindName(k)`, `componentKindName(k)` give a human name for any value.
- The 11 by 11 glyphs live in `gfx/icons.ts` (`ICONS`, drawn by `Icon`); the mockup's new ones (`up`, `down`, `flat`, `lock`, `check`, `plus`, `minus`, `cross`, `hammer`, `box`, `power`, `clock`, `trash`, `flame`, `wrench`, `rocket`, `leaf`, `atom`, `arrowR`, `filter`) are in it. `Icon` takes `class="xs"` (11 px), `"sm"` (14), `"lg"` (33).

### Portraits (`src/lib/gfx/portraits/`)

Officer faces, ported from `mockup/ui/js/portrait.js` with the drawing code and the random-number order unchanged, so the same input gives the same pixels. Import from `#lib/gfx/portraits/index.ts` (also re-exported by `#lib/gfx/index.ts`). It draws without a browser canvas and renders each picture once to a PNG data URL through the icon encoder.

- `portraitBust(spec, style?, over?)` returns the 64 by 72 bust (`PORTRAIT_W`, `PORTRAIT_H`) as a `Sprite` (`{ url, width, height, pixels }`); `portraitHead(spec, style?, over?)` the 32 by 36 head crop of the same picture (`HEAD_W`, `HEAD_H`), for tiles. Both are cached by spec, style and overrides: the same arguments return the same object.
- `spec` is a `PortraitSpec`: `seed`, `age` (from the game clock; it greys the hair and lines the face), `rank` (0 to 5; from 2 a peaked cap is possible, ribbons grow), `branch` (`staff`, `ground` or `governor`, the uniform colour), `gender` (`m` or `f`) and optionally `rolledAt` (`{ age, rank }`). The mockup rolls its traits in one sequence whose length depends on age and rank (greying, the tired eyes after 55, the cap from rank 2), so a bare spec gives another face when the age or rank changes. With `rolledAt` the face (everything but hair colour, age lines, ribbons and whether the cap shows) is rolled at that age and rank and stays; only the hair colour and lines follow `age`, and a cap shows from rank 2 if it was rolled. Leave it out to get the mockup's picture for that exact age and rank; the pixel test does. An officer uses `rolledAt` with their age at the start of the game and a rank of 2 or more.
- `style` is `gritty` (default, `DEFAULT_PORTRAIT_STYLE`) or `clean`; `PORTRAIT_STYLES` lists both with names. The game uses the default; the switch is only on the showcase.
- `traitsOf(spec)` returns the rolled `Traits` (skin, eye colour, hair colour and style, jaw, eyes, brow, nose, mouth, lip, beard, gear, cap, earring, eye shadow); `over` replaces any of them (the showcase uses it to show one option at a time).
- The catalogue: `HAIRS` (21 styles; `hairGenders(id)` and `hairFor(gender)` say who can roll each: men only, women only or both), `BEARDS` (12, men only), `EYES`, `BROWS`, `MOUTHS`, `GEARS` (eyepatch, shades, headset, scar, implant), `SKIN`, `HAIR`, `GREY`, `EYE`, `BALDING` (bald, bald on top and receding: men only), and `ROLLS`, the per-gender tables `traitsOf` picks from.
- Checked against the mockup: `portraits.test.ts` hashes 480 busts and heads (120 seeds, both genders, both styles) and every catalogue option in both styles against the mockup script run in node (fixture `mockup-hashes.json`): identical.
- `Portrait` (`spec`, `view` `bust` or `head`, `scale`, `style`, `over`, `tip`) draws one as a pixelated image. `/dev/portraits` (gallery build) shows the whole catalogue with the Clean and Gritty switch.
- Officers (`screens/commanders/roster.svelte.ts`) carry `gender` and `seed`; `portraitSpec(officer, game.time)` builds the spec (a governor wears the governor uniform, everyone else staff blue). A screen that shows an officer uses it, never its own face.

`tip` everywhere is a `Tip`: a string in the mockup's format (first line the title, then lines; `~` starts a dimmed line, `!` a warning line), or `{ title, lines: { text, tone? }[] }`. Build strings with `tipText(title, ...lines)`, `dim(text)`, `warn(text)`. `materialTip(id, ...extra)`, `buildingTip(id, ...extra)`, `componentTip(id, ...extra)` and `iconTip(ref, ...extra)` give name, category or kind and the dimmed description from the data, and append your lines (numbers, stock, "Short of power"). `materialName(id)`, `buildingName(id)`, `componentName(id)` and `iconName(ref)` are the player-facing names; never show an id.

`use:tooltip={tip}` (from `#lib/ui/index.ts`) puts the same tooltip on any element. The tooltip is one `div#ui-tip` on `body`, made on first use. It follows the pointer (14 px right and 16 px below, flipped left or above at the right and bottom edges, then kept inside the window), opens under an element that gets keyboard focus, closes on Escape, and the innermost element with a tip wins. A tile with an `icons` list shows its own tip, not one per icon.

### Formatting (`src/lib/ui/format.ts`, `fmt` from `#lib/ui/index.ts`)

Pure functions, tested in `format.test.ts`. Quantities come in SI base units as the game holds them (kilograms, kilowatts, newtons, seconds) and leave in the unit the screens show.

- `group(n)` and `count(n)`: whole number with thousands separators. `num(v)`: 0 decimals from 100, 1 from 10, 2 from 0.1, 3 below, `0` under 0.0005.
- `mass(kg)` gives tonnes (`2.5 t`, `0.005 t`), `power(kW)` megawatts, `eflops(v)` compute (`90 EFLOP/s`; `rate` shows it without a period), `thrust(N)` kilonewtons, `people(n)` millions (`8,200 M`), `pct(fraction)`, `amount(a, unit?)` by the material's unit (`kg` as tonnes, `eflops`, `model`).
- `days(d)` (`13 d`, `1.1 y`, `never`) and `duration(seconds)` (`30 s`, `10 min`, `2 h`, then days).
- Gain and loss: `signed(value, text)`, `signedAmount`, `signedPower`, `signedPct` (a zero shows as `0`, no sign); `toneOf(change)` is `cool`, `hot` or `dim`; `trend(net, stock?)` is `up`, `down` or `flat` (flat when tiny against the stock) and `trendTone(trend)` its tone.
- Rates: `PERIODS` (`day`, `year`), `perHour(perSecond)`, `rate(perHour, period, unit?, signed?)` (`24 t/d`, `+8,760 t/yr`, `0`).

## The Economy screen

`screens/economy/Screen.svelte` is a site list and the planet on the left, and on the right one panel with icon tabs and the rate switch (`rates a day | year`, `ui.period`, day by default, read by every rate through `fmt.rate`). It replaces the old Colony screen: `?screen=colony` opens Economy on People, and the map's Selection window opens Economy.

- **Summary**: stat tiles (people with growth, food balance with calories each a day, power, compute, staffing), a calorie bar of what is made by food with the need as a marker, pills for the share eaten, a tile per food, the region and its deposits with their grade (a tile each, from `siteDeposits`), what is short (materials and building groups), industry by kind, programmes running with the count reached, and the builds in progress. Tiles lead to their tab and select there.
- **Production**: kind filter chips and a `prod` tile per building group (output first, building second, count, share running, warn and idle marks). The side card has workers, power, grade, the recipe as icons with rates, switch on or off, and switching a recipe for some of the group (`assign`).
- **Construction**: queue tiles and catalogue tiles (`bld`) by kind, locked ones dimmed with the prerequisites they wait for. The side card is the pick (cost as have and need, recipe, quantity, add) or the selected order (progress, cost, up, down, pause, remove).
- **Stockpiles**: material tiles by category with stock, net gain or loss, a cover bar, category chips, a Show empty toggle and a card with the balance, what extracts it, and the recipes that make and use it at this site.
- **Minerals** (`MineralsTab`, `minerals.ts`): on Earth one tile per reserve with what is left in its basis and the years left, shortest first and the ones not mined last, under 50 years marked; the card has reserves, mined a year, how long they last, accessibility, world output in 2024 and the description. On any other site, the deposits of its body: the atmosphere and the site's own region with exact grades, the other regions with the survey's grade ranges once the body is surveyed (`bodyDeposits`), and a card for the selected one.
- **People**: who lives and works here, jobs by industry, jobs filled, fed and housed.
- **Market** (`MarketTab`): the month's offers as cards (length, pays a month, pays in all, Accept, disabled while too few buildings are free), the contracts (months left, pays a month, a missed delivery) and the ledger card (Next month: the treasury, leases, supply contracts, upkeep, net, and the share of upkeep paid when short). It is the same for every site.
- **Shipyard, Launch, Ships, Supply**: tiles for designs, ships at the pad, ships and supply rows, a card for the selected one, icon lists for cost, propellant and cargo; every control of the tables they replaced is kept. On the Ships tab a jump point is a trip destination and a survey target, and the dock list holds every site a ship reaches from orbit: stations, platforms at a giant and a jump point outpost.
- **Places that are not bodies.** A site's `worldBody` is a body id or a jump point id, so name it with `game.placeName(id)` and find its system with `game.placeSystem(id)`, never `game.body(id)` alone; `siteKind(site)` in `lookup.ts` is the player's word for it (orbital station, surface outpost, atmosphere platform, jump point outpost). The site panel draws a jump point as rings (`drawJumpPoint`) in place of a planet.

`model.ts` holds the pure selectors every tab reads (`stockView`: stock, made, used, net, cover and whether it is short; `groupViews`; `kindTotals`); `tips.ts` the tooltips and rate text; `StockTile` and `GroupTile` are the tiles two tabs share; `TabBody` is the scrolling main column and the 330 px card column. A tab's selection lives in `ui` (`state.svelte.ts`), not in the component, so it survives a screen switch.

## The window manager

`wm` (from `#lib/ui/index.ts`) owns the map desk's windows: docked left (290px), right (310px) or along the bottom (238px), stacked in columns with 8px gutters, or floating. Windows drag by their title bar, re-dock when dropped within 40px of an edge, minimise, close and toggle dock in either mode. `wm.tile()` places them and runs on its own when a window's content or the desk size changes. The Panels popup (Panels in the gear's menu) switches the arrangement, shows and hides windows and resets the layout.

## Scripts and the remote runner

`pnpm check` runs only the legs the change needs and `pnpm check:all` runs all seven. `tools/ci/gate.mjs` reads the same change scope as CI (`tools/ci/scope.json`): it diffs against the merge-base with `origin/dev` (`--base <ref>` overrides; uncommitted and untracked files count), runs `check:types`, `lint`, `knip`, `format:check`, `test`, `test:layout`, `check:tauri` in that order for the legs that are true, prints which run and which are skipped, and stops at the first failure with its exit code. A docs-only change runs none. `node --test 'tools/ci/*.test.mjs'` tests the leg selection. `pnpm check`, `pnpm check:all`, `pnpm test` and `pnpm test:layout` go through `tools/remote/run.mjs`: on that server, or with `CI=true`, they run in place; anywhere else they send the committed `HEAD` to the server over ssh and run it there and never fall back to the local machine; commit first. They forward `SPACE4X_*`, `VITEST_*`, `SHOTS`, `SIZE` and `PORT`; `SPACE4X_FETCH=<dir>` copies a directory back afterwards.

The Playwright web server picks a free port, or uses `PORT` when it is set, so several checkouts can run at once.

## The layout test is the gate for UI work

`tests/layout.spec.ts` loads every query state at 1440x900 (`SIZE=w,h` overrides it) with `?check` and fails with the messages of `src/lib/ui/layoutCheck.ts`: gaps, overlaps, panels off an edge, clipped or cut-off content, cells past an edge, squashed frames, canvases not filling their frames, scroll and empty-space imbalance, overlapping map labels, labels under windows, a wrapped top bar and a scrolling page. A screen whose `Screen.svelte` still renders `<Placeholder` is `fixme`; replacing the placeholder turns its states on, and they must pass before the work is done. `tests/interaction.spec.ts` covers the clock, steps, screen switching and every window operation; `tests/primitives.spec.ts` covers the shared primitives on `/dev/primitives` and the tile kit and icon set on `/dev/tiles`.

For a change to layout or behaviour, also look at the result: `SHOTS=<dir> pnpm test:layout`, then open the PNGs next to the mockup in the same state.

## Conventions

- No comments anywhere: not in code, config or tests. Use clearer names, smaller functions, or a test.
- Never render an internal identifier to the player; show a human label.
- Build only what is named, by the owner, the issue or the validated mockup (`mockup/sketch/`). Implementing an issue, take every figure, label, rule and screen element from the issue and the mockup; where they leave something open or contradict each other, leave that part out rather than guess, keep the rest working, and list it as open on the issue. Do not ask the owner what the issue or mockup already answers. Designing in a mockup, a mechanic, building, screen element, figure, name, number or rule nobody asked for is a question first. Removing or renaming something nobody named is left out the same way. Claude sessions get this rule on every prompt from `.claude/hooks/ask-first.txt`.
- One home for each task. Every action and every figure belongs to one screen or tab, and only that one offers it: Construction queues buildings, Production runs and switches groups, Research assigns labs and scientists, the Shipyard queues ships, Stockpiles shows stock. Another screen may show a tile that opens the home, never a second copy of its control. Before adding a control or a figure, search for where it already lives.
- No explanatory copy. A heading is a name, not a sentence; no subtitles, disclaimers, instructions ("pick a building below and add it"), restated rules or caveats, on screen or in a tooltip. Show figures, states and warnings, and a warning only while it applies. An empty list is empty, not a sentence. If a mechanic needs words to be understood, the screen is missing a figure or a tracker.
- A grouping on screen follows a distinction the game models. Where something stands is the site, chosen in the site list; what kind it is, the kind filter. No section or category exists that the simulation does not.
- Mock content stays visibly mock and in the gallery only: a mock scene or screen carries a "mock scene" tag (`.tag`) on itself. The top bar starts with the game's icon and name, and has no room for a tag beside them at 1440 px.
- Management screens are icon tiles with names, a card for the selected tile, tooltips with a description and the numbers, and one unit per quantity (tonnes, MW, kN, people in millions, rates a day or a year), as in `mockup/ui/` and the section "Icons, tiles and formatting". Tables only where a long list of like rows cannot be tiles. Icons, not text, for screen buttons and status values; no gaps; nothing laid over the map except the windows; one Selection window for whatever is selected; screen buttons switch whole screens, never popups.
- Commit messages say why and how the change was verified.

## Branches, promotion and the desktop build

`dev` is the default branch: features and fixes land on it through pull requests (a feature of ten commits or more) or direct commits (everything smaller), as the global rules say, and CI (`.github/workflows/ci.yml`) runs on pushes to `dev` and `main` and on every pull request. `main` moves only by `pnpm promote`, after a playtest of `dev` in the desktop app. Branch from `dev`, open pull requests against `dev`, and never push `main`.

- `pnpm promote --list` shows the commits and merged pull requests on `origin/dev` that `origin/main` lacks.
- `pnpm promote` merges `origin/dev` onto `origin/main` in the worktree `.claude/worktrees/promote` as branch `promote/main`, pushes that branch, and waits for `.github/workflows/promote.yml` on that commit. It reuses an unchanged candidate (same `main` and `dev` parents). Green, it installs dependencies in the worktree and prints the playtest steps: `./launch.sh` in a checkout of `dev` on the machine that plays it, and `cd .claude/worktrees/promote && ./launch.sh` for the candidate itself. Red, `main` is untouched and the worktree stays for a look.
- `pnpm promote --push` pushes the green candidate to `main` and removes the worktree.
- `promote.yml` runs on `promote/**` pushes and by `workflow_dispatch`: `pnpm check:all` and `pnpm build`. It is listed under `"full"` in `tools/ci/scope.json` because it runs every leg on purpose.

### The desktop build

The game is played as a Tauri 2 app. `src-tauri/` is the shell: `tauri.conf.json` embeds `build/` in the binary through `frontendDist` (no server), names the data directory by the identifier `io.github.bkbf.space4x` (`~/.local/share/io.github.bkbf.space4x`, where WebKit keeps the IndexedDB saves), and opens one frameless, centred window of at least 1100x700. `src/main.rs` creates it, opens the query in `SPACE4X_QUERY` if set, and has three commands: `fullscreen`, `quit` and `report` (a line to stderr). `src/lib/shell/desktop.ts` connects only inside Tauri: it reports `loaded <url>`, uncaught errors, unhandled rejections, `console.error` and a `BENCH` title, and F11 toggles full screen. Bundles (AppImage, deb) are configured with `bundle.active: false`.

- `./launch.sh` installs the locked dependencies, rebuilds the frontend and the release binary only when the files under `src`, `static`, `src-tauri` or the build config differ from the last build (`src-tauri/target/release/.launch-fingerprint`), and starts the window as the transient unit `space4x-window` (`systemd-run --user`), so it outlives the terminal. It waits for the page's `loaded` line in the journal. Closing the window ends the unit; `./launch.sh --stop` stops it.
- `./launch.sh --dev` runs `tauri dev` in the same unit against the vite dev server on a free port on 127.0.0.1, with hot reload; the first start compiles the debug shell.
- `./launch.sh --gallery` builds the gallery into `build-gallery/` and its own binary under `src-tauri/target/gallery` with the identifier `io.github.bkbf.space4x.gallery`, so its storage stays apart; it combines with `--dev`. This is how the gallery is reached.
- `pnpm tauri:build` makes the unbundled release binary `src-tauri/target/release/space4x`; `pnpm tauri` is the Tauri CLI.
- `journalctl --user -u space4x-window` is the window's log. `SPACE4X_QUERY='zoom=system&bench=90' ./launch.sh` runs the map bench in the window and logs its `BENCH` line there. WebKit rounds `performance.now()` to whole milliseconds, so its frame times are coarse.
- `pnpm check:tauri` is `cargo fmt --check` and clippy with warnings as errors; CI runs it as the `tauri` leg, only when `src-tauri/` changes. It needs Rust and the WebKitGTK 4.1 development files.

`deploy/runner/` holds the CI runners: `deploy/runner/setup.sh` registers runner n in `.ci/runners/<n>` of the checkout it is run from, and a failed `layout` or `candidate` job on that runner keeps `layout-results` in `.ci/artifacts/<run id>/` through `gh-issue artifact put`, served at `http://ubuntuserver:8801/Space4x/<run id>/` and linked from the job summary. `.ci/` is ignored globally; never `git clean -x` without `-e .ci`.
